# Meridian — руководство по эксплуатации

Как делать конкретные вещи: первый запуск, ежедневная работа, починка дефектов,
обслуживание проверки. Нормативные документы остаются источником истины; здесь —
маршрут по ним.

Если вы видите систему впервые, начните не отсюда, а со
[`start-here.md`](start-here.md): что это, зачем и как выглядит обычный день, без
терминов. Граница инструмента и проекта описана нормативно в
[`standards/workspace/kernel-boundary.md`](standards/workspace/kernel-boundary.md).

---

## 2. Первый запуск

1. Склонируйте оба репозитория. Kernel и Instance — соседи, не вложение.
2. Установите Node 22+.
3. Включите защиту репозитория (в свежем клоне она выключена):

   ```bash
   git config core.hooksPath hooks
   ```

4. Укажите сессии, где Instance, и убедитесь, что всё подключено:

   ```bash
   export MERIDIAN_INSTANCE=/path/to/instance
   node scripts/preflight.mjs
   ```

   Preflight — это «проверка ремня безопасности»: он громко падает, если
   сессия открыта не против тех корней. Запускайте его первым шагом каждой
   агентной сессии — молчаливая работа со старыми правилами хуже отказа.

5. Прогоните валидатор и тесты (см. §6) — убедитесь, что машина исправна
   до того, как вы её тронули.

Новый продукт (первый день на другом проекте) — отдельный маршрут:
[`instance-template/instance-bootstrap.md`](instance-template/instance-bootstrap.md).

## 3. Ежедневная езда: жизненный цикл задачи

Каждая задача проходит фиксированные фазы —
[`workflows/task-lifecycle.md`](workflows/task-lifecycle.md):

```text
UNDERSTAND → INVESTIGATE → PLAN → IMPLEMENT → VERIFY → REPORT
```

Коротко о духе каждой фазы. UNDERSTAND: классифицируйте задачу (объяснение,
bugfix, фича, намеренное изменение поведения) и зафиксируйте, что именно
запрос разрешает — правки, коммиты, запуск сервисов и внешние эффекты
требуют собственных оснований. INVESTIGATE: границы репозиториев берутся из
inventory-реестра, не из интуиции. PLAN: план — артефакт в `.agent/plans`,
а не сообщение в чате. IMPLEMENT: по применимому протоколу (для багов —
см. §4). VERIFY: минимально достаточное доказательство по маршрутизатору
(§5). REPORT: отчёт-артефакт с тем, что доказано, что нет, и почему.

Рабочая память живёт в `.agent/` Instance: `analysis/`, `plans/`,
`reports/`, `technical-specifications/`, `publication-drafts/` — с
жизненным циклом active → done/archive и Front Matter в каждом артефакте
([`standards/workspace/agent-memory.md`](standards/workspace/agent-memory.md)).
Валидатор предупреждает, когда статус в Front Matter противоречит папке.

## 4. Починка дефектов: bugfix-protocol

Для любого бага действует
[`skills/bugfix-protocol/SKILL.md`](skills/bugfix-protocol/SKILL.md):

```text
REPRODUCE → RED → DIAGNOSE MISS → FIX → GREEN → REPORT
```

Ключевые правила, которые чаще всего нарушают новички: инвариант
формулируется в доменных терминах, без имён функций («отменённая операция
не может быть сохранена», а не «getX возвращает true»); RED — это новое или
аддитивно расширенное утверждение, падающее на дефектной реализации, и вы
обязаны увидеть его падение своими глазами; менять или ослаблять
существующие ассерты без человека нельзя; DIAGNOSE MISS отвечает, почему
существующие тесты дефект пропустили. У протокола пять явных остановок
(неоднозначная классификация, конфликт с существующим ассертом, и т.д.) —
в каждой из них вы останавливаетесь и спрашиваете человека, каким бы
убедительным ни казалось техническое обоснование.

Конвенции конкретного продукта (какие библиотеки, куда класть тест) — не в
протоколе, а в `$MERIDIAN_INSTANCE/skills/bugfix-protocol/context.md`.
Нет файла — это блокер, а не разрешение действовать по памяти.

## 5. Верификация: какое доказательство достаточно

Маршрутизатор — [`verification/README.md`](verification/README.md).
Выбирайте наименьшее доказательство, которое прямо подтверждает
утверждение задачи, а не самый престижный тест: изменили структуру
документа — достаточно статической проверки; чинили поведение — нужен
regression RED/GREEN; утверждаете «работает в браузере» — нужен smoke.

Smoke-прогоны подчиняются
[`verification/smoke-protocol/smoke-protocol.md`](verification/smoke-protocol/smoke-protocol.md):
до действия фиксируется неизменяемый Test Contract, после — только факты в
Execution Context, а вердикт (`PASS` / `FAIL` / `BLOCKED` / `INCONCLUSIVE`)
назначает единственная матрица §11. Красивый экран без собранного
required evidence — это `INCONCLUSIVE`, никогда не `PASS`. Побочные
эффекты имеют три яруса: чтение — свободно, тестовые данные — с основанием,
необратимое/внешнее — только с явным подтверждением человека на конкретное
действие.

Типы доказательств не взаимозаменяемы: smoke PASS не доказывает, что
regression-тест был RED; GREEN не доказывает поведение в браузере. Узкое
доказательство не выдаётся за широкое.

## 6. Обслуживание: валидатор и тесты

```bash
node scripts/kernel-validate.mjs                    # с MERIDIAN_INSTANCE: полная проверка
MERIDIAN_INSTANCE=$PWD/test/instance-fixture \
  node scripts/kernel-validate.mjs                  # как в CI, без приватных данных
node test/kernel-validate.test.mjs                  # правила валидатора сами под тестом
```

Что проверяет валидатор: чистоту всех tracked-файлов Kernel от продуктовых
литералов и личных путей, ссылки, соответствие данных реестров их схемам,
SHA-провенанс завендоренных скиллов, наличие обязательного
Instance-контекста, соответствие записей inventory реальному состоянию
git-репозиториев.

Приборная панель:

| Лампочка | Значение | Ваша реакция |
|---|---|---|
| `FAIL` | Нарушено правило, прогон красный | Чинить до коммита; pre-push не пустит красное |
| `WARN` | Проверка не смогла подтвердить факт | Прочитать; понять, почему; не привыкать |
| `INFO` | Ожидаемое состояние среды | Знать о нём |
| `OK` | Проверено — именно проверено | Ничего |

Прогон без `MERIDIAN_INSTANCE` намеренно красный: он честно объявляет, что
продуктовые литералы не проверялись. Это не поломка.

## 7. Изменение самой системы

Новый файл — сначала классификация по правилу из
[`kernel-boundary.md`](standards/workspace/kernel-boundary.md): «пришлось
бы править это в первый день на другом продукте?» → Instance; «описывает,
как принимать решение, а не что решили?» → Kernel; сомневаетесь → Instance.
Ошибка в сторону Instance стоит одного перемещения, в сторону Kernel —
утечки.

Правило, выстраданное практикой: **новая норма в Kernel приходит вместе с
проверкой, которая её enforce'ит**. Норма без механики — это будущее
расхождение, которое найдёт только следующий аудит.

Каждое изменение Kernel фиксируется в
[`CHANGELOG.md`](CHANGELOG.md) (раздел Unreleased), версия — SemVer в
`VERSION`, совместимость Kernel/Instance объявляется в
[`COMPATIBILITY.md`](COMPATIBILITY.md), а не выводится из номеров. Меняете
валидатор — добавляете кейс в `test/kernel-validate.test.mjs`, который
падает без вашего изменения.

## 8. Сбор обратной связи и метрик

Полная методология: [`standards/workspace/feedback-and-metrics.md`](standards/workspace/feedback-and-metrics.md).
Два независимых потока, оба необязательны, когда сообщать нечего.

**Качественный** — `$MERIDIAN_INSTANCE/.agent/feedback/friction-log.md`.
Одна запись в конце REPORT, только если какое-то правило или документ
Kernel реально мешало задаче. Пустой день — без записи, не запись «трений
не было». Закрытый словарь категорий (`false-positive gate`,
`missing rule`, `unclear wording`, `working-as-intended-but-costly`,
`other`) заставляет назвать тип проблемы, а не просто пожаловаться.

**Количественный** — `node scripts/validate-and-log.mjs` вместо прямого
вызова `kernel-validate.mjs`. Прозрачная обёртка: тот же вывод, тот же код
выхода, плюс одна JSON-строка в
`$MERIDIAN_INSTANCE/.agent/metrics/validate-log.jsonl` — но только против
реального Instance; прогон без Instance или против fixture не логируется,
чтобы не размывать тренд синтетическим шумом. `hooks/pre-push` уже вызывает
обёртку против реального Instance при каждом push (не блокирующе — только
запись метрики), так что данные копятся сами.

Раз в неделю (не жёстче) откройте оба файла: повторяющаяся запись
`false-positive gate`/`missing rule` — кандидат в `CHANGELOG.md` по
обычному циклу «нашли → починили»; растущий, а не плоский тренд `warnings`
в JSONL — повод разобраться, что конкретно копится.

## 9. Чего система не делает никогда

Не хранит секреты — только внешние ссылки на них. Не пишет продуктовые
факты в Kernel. Не угадывает: идентификаторы, владельцев, окружения,
бизнес-процессы. Не назначает вердикты вне §11 и не превращает спорное
поведение в нормативный тест — для расхождений требований/реализации/тестов
есть Problem Record. Не расширяет объём задачи ради верификации. И не
считает молчание согласием: любой обязательный гейт, который не был пройден
явно, — это блокер.

Если вы поймали себя на мысли «да тут очевидно, можно без церемоний» —
перечитайте §1: церемония здесь всегда стоит между вами и правдоподобной
ложью.
