# Архитектура Rust и SQLite для Meridian

> Канонизировано в Kernel 2026-09-19 (`$MERIDIAN_KERNEL/AGENTS.md` §1–§2,
> §10) вместе с четырьмя другими документами программы переноса на Rust;
> ранее велось в отдельном репозитории Instance, теперь замороженном для
> чтения как источник миграции. Содержание решения не менялось при переносе.

Идентификатор решения: `meridian-rust-sqlite-architecture`.

## Контекст

Владелец 2026-09-14 принял направление: завершить и выпустить текущий Meridian
(программа `meridian-operating-upgrade`) как поведенческий эталон, а затем
заменить исполняющую механику Kernel — валидатор, resolver, миграционные и
CLI-операции — реализацией на другом языке
(`$MERIDIAN_KERNEL/governance/meridian-owner-intent-contract.md` §24).
Предыдущий черновик RFC (`meridian-cli-rfc.md`) предлагал Go, отдельный
репозиторий `meridian-cli` и постоянное параллельное хранение Node- и
Go-реализаций. Это решение эти три пункта не наследует: язык, размещение кода
и характер сосуществования с текущей Node-реализацией назначаются здесь заново.

Текущая механика не имеет постоянного хранилища данных рабочего пространства:
Instance сериализуется файлами Markdown/YAML в отдельном Git-репозитории
(`kernel-boundary.md`, `workspace-scope-model.md` §5). Модель логических
областей (`workspace-scope-model.md`) уже отделяет смысл записи от способа
хранения; выбор первого постоянного хранилища должен эту модель не менять, а
реализовать.

## Принятое решение

> **Приоритет решения.** При миграции соблюдение этой архитектуры и применение
> более надёжных возможностей Rust выше буквального или построчного паритета с
> Node.js. Сохраняется бизнес-семантика и обещанный внешний контракт; внутренняя
> слабость Node.js не переносится ради сходства. Полная исполнимая норма —
> `standards/workspace/rust-migration-quality.md`.

1. **Язык — Rust.** Не Go: обоснование прежней ревизии RFC (дешевле разработка
   для одного оператора) уступает требованию управления памятью и
   владением без сборщика мусора для долгоживущей исполняющей механики,
   которой предстоит нести постоянное хранилище и повторяемые миграционные
   операции.
2. **Первая версия — локальный модульный монолит.** Не набор сервисов и не
   клиент-серверная архитектура: один процесс, один устанавливаемый бинарник,
   без сетевого протокола между внутренними частями.
3. **Чистое синхронное предметное ядро.** Домен (типы, области, полномочия,
   происхождение, resolver, конфликты, планы миграции, доказательства,
   вердикты и диагностика) не содержит async, не читает файлы, не обращается
   к Git, базе данных, сети, окружению и не выполняет вывод напрямую.
4. **Порты и адаптеры только на внешних границах.** Файловая система, Git,
   SQLite, вывод в терминал и будущие внешние источники — адаптеры за
   портами (`RecordRepository`, `SourceResolver`, `EvidenceRepository`,
   `GitInspector`, `Clock`); домен зависит от портов, а не от конкретных
   адаптеров.
5. **SQLite — первое локальное постоянное хранилище.** Единственное на первый
   цикл; выбор зафиксирован для локального однопользовательского CLI-сценария,
   не для сервера.
6. **PostgreSQL отложен до подтверждённого серверного сценария.** Не
   отклонён навсегда — просто не входит в первый цикл, пока нет подтверждённой
   потребности в сервере или многопользовательском доступе.
7. **CLI не предоставляет прямой CRUD таблиц.** Команды CLI выражают операции
   предметной области (`import`, `validate`, `resolve`, `migration
   plan|apply|verify|rollback`, `export`), а не произвольные операции над
   строками SQLite-таблиц. Таблицы — деталь адаптера хранения, не поверхность
   CLI.
8. **Канонический JSON остаётся форматом импорта, экспорта и переноса.**
   Независимо от языка реализации и от способа постоянного хранения; это
   продолжает существующий контракт `instance-data-migration.md`
   (нейтральность к хранилищу, свойство 1) и `scoped-record.schema.json`.
9. **Rust и SQLite не меняют логическую модель областей.** Встроенная
   методология, профиль пользователя, профиль организации, рабочее
   пространство проекта, локальная область репозитория и состояние запуска
   (`workspace-scope-model.md` §1) остаются теми же шестью областями; путь
   базы данных, имя таблицы и файл не становятся идентичностью области или
   записи (то же правило, что уже действует для физического пути и
   репозитория, `workspace-scope-model.md`, `kernel-boundary.md`).
10. **Async не проникает в предметное ядро.** Он допускается только в будущих
    внешних адаптерах и только при доказанной фактической потребности — не
    заранее и не по умолчанию.
11. **Собственный unsafe-код запрещён.** `#![forbid(unsafe_code)]` на уровне
    всего workspace; задача не требует работы с небезопасной памятью, и
    исключений для «оптимизации» не предусмотрено.
12. **Big Bang Rewrite отклонён.** Перенос идёт пакетами с непрерывной
    проверкой сохраняемой бизнес-семантики относительно замороженного
    Node-источника, архитектурной приёмкой Rust и явной регистрацией
    намеренных улучшений (`meridian-rust-migration-program-plan.md`), а не
    единым переключением. Паритет внутренней реализации целью не является.
13. **Постоянная двойная реализация отклонена.** Node-реализация — переходный
    поведенческий эталон на время переноса, не постоянная вторая целевая
    реализация; она замораживается на конкретной ревизии и удаляется только
    после доказанного сохранения бизнес-контракта, выпуска Rust Meridian и отдельного решения
    владельца.
14. **Отдельные микросервисы отклонены.** Первая версия не декомпозируется на
    сетевые сервисы ни на уровне домена, ни на уровне хранения.

## Обоснование

Задача исполняющей механики Kernel — файлы, Git, YAML, JSON Schema,
детерминированные проверки и, теперь, локальное хранилище — не требует
сетевого сервиса и не эксплуатирует конкурентный доступ нескольких клиентов:
она выполняется одним оператором на одной машине. Модульный монолит с чистым
синхронным ядром даёт те же гарантии корректности предметной логики, что и
более сложная архитектура, без стоимости распределённой системы, которую
некому обслуживать.

Порты и адаптеры на границе (а не сквозь всё ядро) позволяют заменить SQLite
другим хранилищем или добавить сетевой адаптер в будущем без переписывания
домена — то же разделение, которое `workspace-scope-model.md` уже требует от
данных: сначала логическая область, потом способ хранения.

SQLite даёт транзакционную локальную персистентность без установки и
администрирования сервера базы данных — соответствует масштабу «один
оператор, одна машина», для которого написан этот ADR. PostgreSQL решает
проблему, которой ещё нет (конкурентный многопользовательский доступ), и его
преждевременное введение добавило бы операционную сложность без
подтверждённой потребности.

Запрет `unsafe` и синхронное ядро снижают поверхность дефектов ровно там, где
у системы нет технической причины идти на этот риск: задача не работает с
низкоуровневой памятью и не обслуживает конкурентные сетевые запросы.

## Последствия

- Целевая структура Cargo workspace (`meridian-core`, `meridian-app`,
  `meridian-storage-sqlite`, `meridian-cli`), схема SQLite и типы предметной
  области фиксируются отдельной технической спецификацией
  (`meridian-rust-target-architecture.md`), которую это решение не
  дублирует.
- Порядок пакетов, ворота и выпускной рубеж переноса — отдельный план
  (`meridian-rust-migration-program-plan.md`), активируемый только после
  выпуска и интеграции `meridian-operating-upgrade-release`
  (`meridian-owner-intent-contract.md` §24).
- CLI RFC (`meridian-cli-rfc.md`) детализирует состав команд и маршрут
  постепенного замещения Node-реализации; он принимает это решение как
  данность и не пересматривает язык, монолит, границы портов или выбор
  SQLite.
- Существующий контракт `instance-data-migration.md` (нейтральность к
  хранилищу, точный источник, обратимость, проверяемое соответствие)
  остаётся действующим и не переписывается ради этого решения: перенос на
  SQLite обязан удовлетворять тем же девяти свойствам, что уже проверяются
  для переходного Экземпляра.
- Будущее подключение PostgreSQL или сетевого API, если оно понадобится,
  потребует отдельного ADR — это решение его не предрешает и не запрещает,
  оно просто исключает его из первого цикла.

## Альтернативы

1. **Go.** Дешевле по времени разработки для одного оператора, даёт
   однофайловый кросс-платформенный бинарник почти так же просто, как Rust.
   Отклонён этим решением владельца: язык исполняющей механики Meridian —
   Rust, не Go (`meridian-owner-intent-contract.md` §24). Ранее рассмотренные
   технические доводы за Go (простота `go-git`, скорость разработки) не
   перевешивают решение владельца и не открывают язык к пересмотру заново
   в рамках этого документа.
2. **Оставить Node.js с проверенными npm-зависимостями вместо самодельных
   парсеров.** Не решает целевую задачу — замену исполняющей механики и
   введение постоянного хранилища; рассмотрена и отклонена как не отвечающая
   принятому направлению.
3. **PostgreSQL как первое хранилище.** Отклонён: требует сервера базы
   данных для локального однопользовательского сценария, для которого нет
   подтверждённой потребности в конкурентном доступе.
4. **Полная переработка на микросервисы уже в первой версии.** Отклонена:
   несоразмерная стоимость для одного оператора и локального сценария
   использования; не отвечает ни одному подтверждённому требованию.
5. **Big Bang Rewrite — переключение одним изменением без промежуточного
   паритета.** Отклонён: делает невозможным механическое доказательство
   сохранения поведения и лишает владельца точки отката на каждом шаге.

## Ограничения

- Это решение не выбирает конкретные Rust-крейты (YAML, JSON Schema,
  SQLite-драйвер) — это предмет реализации на этапе `rust-workspace-foundation`
  (`meridian-rust-migration-program-plan.md`), а не архитектурного решения.
- Это решение не назначает точный номер версии Rust Meridian и не начинает
  сам перенос — оно фиксирует архитектуру, к которой перенос обязан прийти.
- Это решение не отменяет и не изменяет выпускной рубеж текущей программы
  `meridian-operating-upgrade` — она остаётся обязательным предшествующим
  условием (`meridian-owner-intent-contract.md` §24).
- Это решение не решает вопрос публичного релиза или распространения
  стороннему пользователю — это отдельные открытые решения (`README.md`
  D-4/D-5), которых оно не закрывает.
