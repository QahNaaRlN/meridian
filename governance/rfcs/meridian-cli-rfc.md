# Meridian CLI — единый устанавливаемый CLI на Rust поверх Cargo workspace

## Резюме

Перенести механическую часть Kernel — валидатор, preflight, обёртку метрик,
bootstrap и последующие операции разрешения норм, импорта, миграции и экспорта
данных рабочего пространства — на один устанавливаемый CLI-бинарник, собираемый
из **Cargo workspace, размещённого в самом репозитории Kernel**:
`meridian init | doctor | import | validate | resolve | migration
plan|apply|verify|rollback | export`. Нормативная часть (стандарты, протоколы,
скиллы, шаблоны) остаётся текстом на месте — она не переписывается ни на каком
языке ни сейчас, ни в целевом состоянии; CLI её только читает, проверяет и
раскладывает.

Первым постоянным хранилищем данных рабочего пространства становится SQLite,
как уже решено отдельным ADR (`meridian-rust-sqlite-architecture.md`). Этот RFC
данное архитектурное решение не пересматривает — он раскрывает его для
CLI-поверхности и описывает маршрут перехода от текущей Node-реализации.

Node-реализация замещается **постепенно, через доказанное сохранение
бизнес-контракта и архитектурную квалификацию**, а не
одномоментно и не как постоянная вторая реализация: она замораживается на
точной ревизии выпуска `meridian-operating-upgrade-release` и остаётся
источником бизнес-семантики и fixtures до выпуска Rust Meridian. Намеренные
Rust-native улучшения не обязаны повторять Node.js; они должны быть явно
обоснованы и протестированы. Удаление Node — предмет отдельного решения
владельца **после** выпуска, а не часть настоящего RFC.

## Контекст и проблема

Механическая часть Kernel сейчас (ревизия `VERSION` **0.5.0**) — это более
десяти артефактов на Node.js:

| Артефакт | Роль |
|---|---|
| `scripts/kernel-validate.mjs` (~3300 строк) | Проверки гейта по всем принятым пакетам операционной модели |
| `scripts/preflight.mjs` | Проверка проводки сессии (`MERIDIAN_KERNEL`/`MERIDIAN_INSTANCE`) |
| `scripts/validate-and-log.mjs` | Обёртка с записью метрик прогона |
| `scripts/rule-resolver.mjs` | Разрешение применимых норм |
| `scripts/validate-branch-name.mjs` | Синтаксическая проверка имени ветки |
| `scripts/lib/*.mjs` (14 модулей) | Композитные проверки отдельных контрактов операционной модели (реестр источников, приём правил, режим совместимости, миграция данных Экземпляра, состояние выполнения, роли, контекст, доказательства и др.) |
| `scripts/lib/yaml.mjs`, `scripts/lib/json-schema.mjs` | Самодельные YAML-парсер и подмножество JSON Schema |
| `test/*.test.mjs` (~5000 строк, включая `test/kernel-validate.test.mjs`) | Регрессионные наборы, включая adversarial-кейсы |
| `hooks/pre-push` | `#!/bin/sh`, запускает проверки перед push |
| `.github/workflows/gate.yml` | То же в CI, через `setup-node` |

Объём вырос на порядок с ревизии 0.3.0, для которой этот RFC создавался
изначально: за это время добавлены каталог типов задач, контракт постановки
задачи, модель состояния выполнения, роли и управление человеком, манифест
контекста, контракт доказательств и передачи, полевая оценка, реестр источников
инструкций, приём внешних правил, режим совместимости и контракт миграции
данных Экземпляра. Это увеличивает, а не снимает актуальность проблемы, ради
которой писался этот RFC:

1. **Скрытая зависимость от Node.js.** Каждый запуск любой из этих проверок
   предполагает установленный Node 22+. На новой машине, у нового оператора или
   в CI-окружении без Node это не работает без отдельного шага установки.
2. **Риск в собственном коде разбора.** `scripts/lib/yaml.mjs` и
   `scripts/lib/json-schema.mjs` — не продукт этой системы, а инфраструктурная
   случайность: их пришлось написать из-за отсутствия зависимости от npm.
   Каждый найденный в них дефект — это время, потраченное на проверку кода,
   который для любой другой системы был бы библиотекой с историей issue-трекера
   и тестов на порядки больше, чем написанного здесь.
3. Открытое решение D-4 в `README.md` («нужен ли bootstrap CLI/installer для
   сценария коммерческой передачи») по существу эквивалентно этому предложению
   и не закрыто.
4. Рост объёма композитных проверок (`scripts/lib/*.mjs`) увеличивает
   поверхность бизнес-семантики, которую нужно классифицировать, типизировать
   и проверить при переносе, и делает откладывание переноса дороже с каждым
   принятым пакетом операционной модели.

## Движущие факторы и ограничения

- Кросс-платформенность (Windows у текущего оператора, потенциально
  Linux/macOS у будущих) без требования к установленному рантайму.
- Минимизация собственного кода, критичного для целостности единственной
  механической гарантии системы (purity gate и композитные проверки
  контрактов операционной модели).
- Совместимость с духом системы: никакая замена не должна изменить наблюдаемое
  поведение без явного паритетного прогона (см. «Критерии успеха»).
- Решение владельца 2026-09-14 сузило это предложение: первая цель — не
  публичный инструмент и не сервер, а локальный однопользовательский CLI
  поверх модульного монолита с SQLite (`meridian-owner-intent-contract.md`
  §24, `meridian-rust-sqlite-architecture.md`).

## Цели и не-цели

**Цели:**

- Один устанавливаемый статический бинарник на все команды, без внешних
  рантайм-зависимостей.
- Замена самодельных YAML/JSON Schema парсеров проверенными библиотеками —
  **с сохранением текущей строгости отдельным слоем** (см. «Строгость как
  правило»).
- Полный паритет поведения с Node-реализацией на момент заморозки эталона: тот
  же набор проверок, те же коды выхода, то же множество FAIL/WARN по
  содержанию.
- Перенос существующих регрессионных наборов (`test/*.test.mjs`) как
  адаптированного эталонного набора для новой реализации, до основной логики
  порта, а не после.
- Паритет проверяется механически и непрерывно во время переноса — до
  переключения хуков и CI на Rust, а не разово перед ним.
- Первое постоянное хранилище — SQLite (`meridian-rust-sqlite-architecture.md`).

**Не-цели:**

- **Постоянная двойная реализация.** Node не остаётся навсегда второй
  постоянной реализацией. Она замораживается как эталон на точной ревизии
  `meridian-operating-upgrade-release` и удаляется только после доказанного
  паритета, выпуска Rust Meridian и отдельного решения владельца (см.
  «Миграция и rollout»).
- **Отдельный репозиторий `meridian-cli`.** Rust-код размещается в
  репозитории Kernel как Cargo workspace, а не в отдельном release unit.
- **PostgreSQL, серверный режим, сетевой API.** Вне первого цикла
  (`meridian-rust-sqlite-architecture.md`).
- Переписывание стандартов, протоколов или скиллов — они остаются
  Markdown/YAML и не становятся частью бинарника как логика.
- Публичный релиз или дистрибуция стороннему пользователю в рамках этого
  RFC — отдельное решение (связано с D-4/D-5 в `README.md`).
- Расширение функциональности валидатора одновременно с переносом. Сначала
  паритет, затем — новые возможности отдельными изменениями. Правило,
  добавленное в Node-реализацию **до** заморозки эталона (D-H), этой не-цели
  не нарушает; после заморозки Node-реализация не правится вовсе, даже когда
  при портировании видно, что в оригинале сделано неудачно, — такие находки
  записываются в список и вносятся после квалификации паритета.

  **Эта не-цель не относится к `init`/`import`/`export`/`migration
  plan|apply|verify|rollback` и к самому хранилищу SQLite** (пакеты 6–8
  `meridian-rust-migration-program-plan.md`). У них нет прямого эквивалента в
  сегодняшней Node-реализации, но они не являются новой функциональностью в
  запрещённом здесь смысле: они реализуют контракты, уже принятые до этого
  RFC (`instance-data-migration.md`, `controlled-rule-intake.md`,
  `existing-project-compatibility-mode.md`, `workspace-scope-model.md`) и
  зафиксированные `meridian-rust-sqlite-architecture.md`/
  `meridian-rust-target-architecture.md`, а не изобретают новое поведение.
  Строгий паритет с замороженным эталоном обязателен именно для того, что уже
  есть в Node — прежде всего `validate`/`resolve` и существующих композитных
  проверок контрактов операционной модели (`scripts/lib/*.mjs`); эти пакеты
  не должны менять семантику ни одной из них и не должны добавлять
  постороннюю функциональность сверх того, что уже определяют перечисленные
  контракты и техническая спецификация.

## Предлагаемое решение

### Выбор языка и расположения: Rust, Cargo workspace в Kernel (решения D-D наследуются от ADR)

Язык и общая архитектура (модульный монолит, чистое синхронное предметное
ядро, порты и адаптеры на внешних границах, `#![forbid(unsafe_code)]`) приняты
отдельным ADR `meridian-rust-sqlite-architecture.md` и здесь не пересматриваются.
Целевая структура Cargo workspace (`meridian-core`, `meridian-app`,
`meridian-storage-sqlite`, `meridian-cli`) и границы крейтов —
`governance/specifications/meridian-rust-target-architecture.md`.

Rust-код размещается в этом же репозитории Kernel, а не в отдельном
репозитории `meridian-cli`: он читает те же нормативные Markdown/YAML/JSON
Schema документы Kernel, что и сегодняшняя Node-реализация, и отдельный
release unit создавал бы риск рассинхронизации версии CLI и версии
методологии, которую он проверяет.

### Строгость как правило Kernel, а не как ограничение реализации (решение D-A)

Самодельные парсеры не просто разбирают вход — они **отвергают всё, что не
реализуют**, и на этом стоят существующие регрессионные adversarial-кейсы
(например: непокрытый `patternProperties` обязан покрасить гейт; `format:
email` обязан покрасить гейт). Проверенные Rust-библиотеки (`serde_yaml` или
аналог, `jsonschema` с поддержкой draft-07) поддерживают заметно больше
входного языка: подставленные «как есть», они сделают эти кейсы зелёными — то
есть паритет провалится не из-за дефекта порта, а из-за самого факта «взять
библиотеку».

Решение (наследуется без изменений по существу от предыдущей ревизии этого
RFC): **строгость сохраняется отдельным слоем поверх библиотек.**

- Перед валидацией дерево схемы обходится целиком и отвергается любой ключ вне
  списка поддерживаемых и любой `format` вне поддерживаемого набора — прямой
  эквивалент существующего `assertSupportedDeep` (`scripts/lib/json-schema.mjs`).
- YAML сначала проходит собственный strict-lint (табы в отступе, `---` со
  второй строки, `&`/`*`/`!`, flow-стиль — та же дисциплина, что несёт
  сегодняшний `scripts/lib/yaml.mjs`), и только потом отдаётся библиотеке.

Allowlist остаётся явным правилом Kernel — его место в
`standards/workspace/kernel-boundary.md`, а не в комментарии к коду.

Этот слой строгости реализуется пакетом `rust-source-format-adapters`
(пакет 4 `meridian-rust-migration-program-plan.md`), а не пакетом 2
(`rust-conformance-harness`): пакет 2 создаёт независимый инструмент
сравнения, но не переносит ни строчки самого YAML/JSON Schema кода — это
предыдущая ревизия плана смешивала по ошибке (см. «Миграция и rollout»).

Отклонённая альтернатива: принять расширенное поведение библиотек и вывести
соответствующие adversarial-кейсы из набора. Это изменение нормативного
поведения гейта — гейт начал бы пропускать данные, которые раньше отвергал —
и потому отклонено.

### Состав CLI

```text
meridian init                     # инициализация локального рабочего пространства и SQLite
meridian doctor                   # эквивалент scripts/preflight.mjs плюс проверка состояния хранилища
meridian import                   # управляемый приём внешних правил и данных Экземпляра
meridian validate                 # эквивалент scripts/kernel-validate.mjs
meridian validate --log-metrics   # эквивалент scripts/validate-and-log.mjs
meridian resolve                  # эквивалент scripts/rule-resolver.mjs
meridian migration plan           # план миграции, не изменяет состояние
meridian migration apply          # применение плана, с dry-run и явным подтверждением
meridian migration verify         # проверка результата миграции
meridian migration rollback       # обратимое восстановление по payload.rollback
meridian export                   # канонический экспорт в JSON
```

`--format human|json` поддерживается всеми командами, вывод результата — в
stdout, диагностика — в stderr, коды завершения стабильны. Точный состав полей
и кодов — предмет технической спецификации
(`meridian-rust-target-architecture.md`), а не этого RFC.

`init` создаёт необходимые базы `tool`/`workspace` каждую со своей явной
ролью и совместимой редакцией Kernel — роль читается из метаданных базы, а
не выводится из имени или расположения файла
(`meridian-rust-migration-program-plan.md` §5.4, пункт 1). `doctor` обязан
показывать роль и редакцию каждой открытой базы как часть проверки
состояния хранилища. `import` направляет продуктовые записи только в базу
роли `workspace` — база `tool` не становится вторым продуктовым каноном.
`export` объединяет только то, что каждая база реально хранит для своей
роли, никогда не копируя записи между ролями. Ни одна из этих четырёх команд
не реализуется этим корректирующим пакетом (`knowledge-agent-foundation`) —
основание для их однозначной будущей реализации фиксируется здесь и в
технической спецификации, сама реализация остаётся за пакетами
`meridian-cli-foundation`/`meridian-cli-migration`.

Паритетный харнесс (см. решение D-F) командой CLI **не является** и в этот
список не входит — он отдельный артефакт по причинам, изложенным ниже.

Библиотеки: YAML-парсер, JSON Schema-валидатор с поддержкой draft-07,
`rusqlite` или аналог для SQLite. Выбор конкретных крейтов фиксируется на этапе
реализации (пакет `rust-workspace-foundation`,
`meridian-rust-migration-program-plan.md`), а не в этом RFC.

### Расположение `instance-template` и источник шаблона (решение D-C)

`bootstrap`/`init` читает `instance-template/` **из `$MERIDIAN_KERNEL`**, а не
из вшитой в бинарник копии. Обоснование не изменилось с прежней ревизии этого
RFC: шаблон — нормативный артефакт Kernel и меняется вместе с правилами;
вшитая копия создала бы второй источник правды и сценарий, в котором `init`
отрабатывает зелёным, а `validate` следом краснеет, причём по выводу
невозможно отличить «данные заполнены неверно» от «шаблон устарел
относительно валидатора». Самодостаточности это всё равно не даёт: `validate`
читает схемы реестров Kernel, `PIN.yaml` скиллов и список файлов для
purity-скана; бинарник без Kernel разложит шаблон, но не сможет его проверить.

### Паритетный харнесс и `hooks/pre-push` (решение D-F)

Харнесс запускает обе реализации на одних и тех же деревьях и сравнивает
множества FAIL/WARN по содержанию, а не последовательность команд — это не
последовательность вызовов, а разбор вывода, и место его жизни надо выбрать
явно.

**Харнесс — отдельный артефакт, а не команда CLI и не тело хука.**
`hooks/pre-push` во время переходного периода запускает обе реализации через
харнесс; `.github/workflows/gate.yml` вызывает тот же харнесс. Одна реализация
последовательности на оба места.

Причина, по которой харнесс не встраивается ни в `meridian` (Rust), ни в
Node-реализацию: бинарник стал бы судьёй в споре, где он сам сторона. Дефект
одной реализации смог бы замаскировать сам себя — например, если нормализация
вердиктов окажется чуть агрессивнее, чем следует, — и независимая проверка
перестала бы быть независимой ровно тогда, когда она нужна.

**Порядок появления сравнения.** Пакет 2 (`rust-conformance-harness`) создаёт
сам инструмент — независимый механизм запуска, нормализации и сравнения
вердиктов — раньше, чем существует хоть одна перенесённая на Rust
возможность. До появления Rust-реализации харнесс проверяется на
контролируемом корпусе: заведомо совпадающих парах вердиктов и намеренно
расходящихся парах, подставленных для проверки, что харнесс действительно
обнаруживает расхождение, а не молчит на любом входе. Реальное сравнение
Node/Rust-вердиктов появляется только с пакета 4
(`rust-source-format-adapters`) и дальше наращивается ровно на ту
поверхность, которую вводит каждый следующий пакет (5–8) — не на весь объём
сразу.

**`hooks/pre-push` остаётся `#!/bin/sh`** во время переходного периода — та же
причина, что и в предыдущей ревизии: `core.hooksPath hooks` указывает на один
версионируемый каталог, а `hooks/pre-push` — один файл; нативный бинарник туда
не кладётся без потери кроссплатформенности каталога `hooks/` или появления
двоичного артефакта, не покрытого purity-сканом. После полного переключения на
Rust (см. «Миграция и rollout», шаг с удалением Node) хук может звать
`meridian validate` напрямую без харнесса — эта дальнейшая упрощённая форма не
входит в объём настоящего RFC и фиксируется отдельным изменением после
квалификации паритета.

## Альтернативы

1. **Оставить Node.js, добавить проверенные npm-зависимости** (`yaml`, `ajv`,
   `simple-git`) вместо самодельных парсеров. Дешевле по времени, не решает
   проблему рантайм-зависимости и кросс-платформенной поставки одним файлом.
   Отклонена как половинчатая.
2. **Go вместо Rust.** Рассматривался и был предпочтён в предыдущей ревизии
   этого RFC ради более дешёвой разработки для одного оператора. Отменён
   решением владельца 2026-09-14: `meridian-owner-intent-contract.md` §24 и
   `meridian-rust-sqlite-architecture.md` закрепляют Rust, а не Go, как язык
   исполняющей механики Meridian. Не сохраняется даже как рассмотренная
   равноправная альтернатива дальше этого пункта.
3. **Отдельный репозиторий `meridian-cli`.** Рассматривался в предыдущей
   ревизии как независимый release unit. Отклонён этой ревизией: единый
   репозиторий Kernel снимает риск рассинхронизации версии CLI и версии
   нормативной методологии, которую он проверяет (см. «Предлагаемое решение»).
4. **Постоянная двойная реализация Node + новый язык.** Рассматривалась и была
   принята в предыдущей ревизии этого RFC как постоянное решение. Отменена
   решением владельца 2026-09-14: JavaScript-реализация служит переходным
   источником бизнес-семантики до доказанного сохранения контракта, но не сохраняется как
   постоянная вторая реализация.
5. **Ничего не менять.** Валидатор работает, регрессионные наборы зелёные.
   Риск не острый, но объём собственного кода композитных проверок вырос на
   порядок с прошлой ревизии этого RFC, и стоимость переноса растёт быстрее,
   чем откладывание переноса её снижает. Отклонена по той же причине, что и
   раньше, усиленной ростом объёма.

## Компромиссы

Плюс: снимается рантайм-зависимость, устраняется самый рискованный собственный
код (самодельные YAML/JSON Schema парсеры), первое постоянное хранилище
(SQLite) заменяет неявное отсутствие персистентности, а conformance-прогон двух
реализаций во время переноса проверяет сохраняемые контракты на протяжении всего
переходного периода.

Минус: перенос — не бесплатная операция. Объём композитных проверок
(`scripts/lib/*.mjs`, 14 модулей на момент этой ревизии) означает, что
каждый бизнес-контракт придётся типизировать и доказывать отдельно, а не одним
монолитным диффом; каждое намеренное изменение поведения требует явного
Rust-native обоснования, записи совместимости и теста.
Смягчение: заморозка и порядок пакетов (`meridian-rust-migration-program-plan.md`)
делают момент, когда правило можно менять, а когда нельзя, однозначным, а не
предметом суждения по ходу работы.

## Миграция и rollout

0. **Node-эталон замораживается на ревизии `meridian-operating-upgrade-release`
   (решение D-H).** Это не дата начала работы над отдельным репозиторием (как
   было в предыдущей ревизии), а конкретный принятый и выпущенный релиз
   Kernel — выпускной рубеж уже завершённой программы `meridian-operating-upgrade`
   (Kernel `0.6.0` выпущен; порядок и рубеж той программы зафиксированы в
   замороженном историческом источнике происхождения, не действующей
   зависимости этого RFC). Причина не организационная: при подвижном эталоне
   расхождение в
   паритетном прогоне становится неинтерпретируемым — оно может означать и
   дефект порта, и то, что Node ушёл вперёд. Заморозка на конкретном выпуске, а
   не на дате, делает точку сравнения воспроизводимой независимо от момента
   фактического запуска порта.
1. Cargo workspace создаётся внутри репозитория Kernel (пакет
   `rust-workspace-foundation`).
2. **Харнесс соответствия** (решение D-F, пакет `rust-conformance-harness`)
   создаётся как отдельный, независимый от Rust-реализации артефакт — раньше,
   чем существует хоть одна перенесённая возможность. На этом шаге он
   проверяется только на контролируемом корпусе заведомо совпадающих и
   намеренно расходящихся пар вердиктов — реального сравнения Node/Rust здесь
   ещё нет, потому что нет ни строчки перенесённого кода. Слой строгости
   (D-A) в объём этого пакета не входит.
3. Предметное ядро — `meridian-core`: типы, resolver, конфликты, планы
   миграции, доказательства, вердикты и диагностика (пакет `rust-domain-core`).
   Бизнес-правила сохраняются, но моделируются Rust-native типами и
   инвариантами, а не построчным переносом.
4. **Слой строгости (решение D-A)** реализуется и покрывается юнит-тестами как
   адаптеры исходных форматов — `assertSupportedDeep`, allowlist форматов,
   strict-lint YAML и совместимые входные контракты
   `scripts/lib/yaml.mjs`/`scripts/lib/json-schema.mjs` (пакет
   `rust-source-format-adapters`). С
   этого пакета харнесс (пакет 2) начинает реальное сравнение Node/Rust —
   впервые на этой поверхности, а не на контролируемом корпусе.
5. Разрешение норм — порт `scripts/rule-resolver.mjs` и композитных проверок
   контрактов операционной модели (`scripts/lib/*.mjs`) поверх портов
   `meridian-core` (пакет `rust-rule-resolution`). Сравнение харнесса
   расширяется на эту поверхность.
6. Хранилище SQLite (пакет `sqlite-storage-adapter`): схема, транзакционная
   запись, включённые foreign keys, неизменяемые редакции, идемпотентный
   импорт, канонический экспорт.
7. Основа CLI (пакет `meridian-cli-foundation`): `init`, `doctor`, `validate`,
   `resolve`, `export`.
8. Миграционный CLI (пакет `meridian-cli-migration`): `import`, `migration
   plan|apply|verify|rollback` — реализация контракта
   `instance-data-migration.md` поверх `meridian-storage-sqlite`. Пакет
   обязан доказать полный импорт всех записей из применимого источника,
   эквивалентность применимых норм, идемпотентность и обратимость (§
   «Критерии успеха»), а не только успешное выполнение команды. Эта команда
   не является универсальным ingestion API Metis: она не подключает
   Confluence, Git/Markdown knowledge source или code repository и не строит
   snapshot/index/graph. Такие источники подключаются отдельными adapters по
   `metis-federated-knowledge-architecture.md`.
9. **Квалификация бизнес-контракта** (пакет
   `rust-business-contract-qualification`): харнесс
   запускается на одних и тех же деревьях — реальном Instance, синтетическом
   Instance (`test/instance-fixture`), без Instance, и на всех
   adversarial-кейсах перенесённого набора — на полном объёме перенесённой
   механики, накопленном пакетами 2–8. Сохранённые контракты обязаны совпасть;
   намеренные Rust-native улучшения имеют отдельные ожидаемые результаты,
   бизнес-обоснование и тест. Только необъяснённое расхождение — блокер. После
   первого чистого полного
   прогона `hooks/pre-push` и `.github/workflows/gate.yml` переключаются на
   вызов харнесса, запускающего обе реализации.
10. **Выпуск Rust Meridian** (пакет `meridian-rust-release`): один
    устанавливаемый бинарник, Node.js не требуется для его работы, SQLite
    создаётся и открывается автоматически, применимый замороженный Instance
    (§ «Критерии успеха») импортируется, вердикты совпадают с эталоном, и
    переходный `MERIDIAN_INSTANCE`-адаптер отключён.
11. **Удаление Node-реализации — отдельное решение владельца после выпуска.**
    Оно не входит в этот RFC и не происходит автоматически по факту выпуска:
    `meridian-owner-intent-contract.md` §24 требует доказанного сохранения
    бизнес-контракта, выпуска Rust Meridian и отдельного решения для удаления
    Node-реализации.

## Критерии успеха

- Квалификация бизнес-контракта: необъяснённых расхождений нет; сохранённые
  контракты совпадают, а каждое намеренное Rust-native улучшение обосновано,
  отражено в совместимости и покрыто тестами на всех классах деревьев.
- Итоговый CLI собирается в один устанавливаемый бинарник под
  Windows/Linux/macOS.
- `init` на пустом каталоге производит структуру, идентичную
  `instance-template/` текущего `$MERIDIAN_KERNEL` (файл-в-файл, сверка
  `diff`, не «по духу»), и создаёт открываемую базу SQLite.
- Ни один нормативный документ Kernel не потребовал изменения содержания ради
  переноса — кроме `kernel-boundary.md`, куда переезжает явная формулировка
  allowlist'а (D-A), ранее существовавшая только как комментарий в коде.
- Применимый замороженный источник миграции (текущий продуктовый Instance,
  замороженный для чтения — `AGENTS.md` §1–§2) успешно импортируется, и
  вердикты `validate`/`resolve` совпадают с Node-эталоном на замороженной
  ревизии.

## Риски

- **Дрейф двух реализаций во время переноса.** Правило, внесённое в одну
  реализацию и забытое в другой, ловится только паритетным шагом. Если этот
  шаг когда-нибудь отключат «на время», переходный период потеряет свою
  единственную гарантию, не заметив этого.
- **Харнесс сам не покрыт паритетом.** У него одна реализация, и его
  собственный дефект — слишком агрессивная нормализация вердиктов — выглядит
  снаружи как «расхождений нет». Смягчение: держать его намеренно примитивным
  и покрыть тестами на заведомо **расходящихся** входах, а не только на
  сходящихся.
- **Расхождения, невидимые для паритета сообщений.** Порядок ошибок и
  усечение вывода должны быть детерминированы по обе стороны — иначе
  усечение начнёт резать *другие* ошибки при одинаковом их множестве.
- `forbidden_patterns` из `product.yaml` — это JS RegExp; выбранная Rust-крейт
  для регулярных выражений может не поддерживать те же конструкции (lookahead,
  backreference). Паттерны обязаны проверяться на компилируемость с явным
  FAIL, а не молча пропускаться.
- Библиотека JSON Schema может расходиться с ручной реализацией на
  `if/then/else` и на кастомных проверках форматов — требует сверки на
  кейсах, а не предположения о совместимости.
- Объём переносимых композитных проверок (14 модулей `scripts/lib/*.mjs` на
  момент этой ревизии, и он может вырасти к моменту заморозки эталона) —
  риск недооценки объёма порта относительно прежней ревизии этого RFC, писавшейся
  для одного валидатора и preflight.
- Единственный оператор — весь план держится на одном человеке; риск тот же,
  что и у системы в целом, не новый для этого RFC.

## Открытые вопросы

- Стоит ли переносить `smoke-protocol`/`bugfix-protocol` SHA-provenance
  проверку в Rust-реализацию как есть, или это повод пересмотреть формат
  пиннинга (вне объёма этого RFC, фиксируется отдельно, если возникнет).
- Точный маршрут упрощения `hooks/pre-push` после удаления Node (см.
  «Миграция и rollout», шаг с удалением Node-реализации) — предмет отдельного
  изменения после квалификации паритета, не этого RFC.
