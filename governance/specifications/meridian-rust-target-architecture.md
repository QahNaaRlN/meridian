# Целевая архитектура Rust Meridian

> Канонизировано в Kernel 2026-09-19 (`$MERIDIAN_KERNEL/AGENTS.md` §1–§2,
> §10) вместе с четырьмя другими документами программы переноса на Rust;
> ранее велось в отдельном репозитории Instance, теперь замороженном для
> чтения как источник миграции. Содержание спецификации не менялось при
> переносе.

Идентификатор спецификации: `meridian-rust-target-architecture`.

Этот документ детализирует архитектурное решение
`meridian-rust-sqlite-architecture.md` (`accepted`) до уровня, достаточного для
начала реализации: границы крейтов Cargo workspace, схема SQLite, состав
типов предметной области и поверхность CLI. Он не пересматривает язык,
монолитную форму, границы портов и выбор SQLite — они приняты тем ADR.
Порядок пакетов, ворота и выпускной рубеж переноса — отдельный план
(`meridian-rust-migration-program-plan.md`), не этот документ.

## 1. Cargo workspace

Один Cargo workspace в репозитории Kernel, четыре крейта:

```text
meridian-core            # предметное ядро — без файлов, Git, БД, сети, env, вывода
meridian-app             # порты и оркестрация — определяет traits, не реализует ни один
meridian-storage-sqlite  # адаптер хранения — единственный крейт, знающий про SQLite
meridian-cli             # корень композиции: бинарник + все локальные адаптеры портов,
                          # не реализованные meridian-storage-sqlite (файловая система,
                          # Git, окружение, Clock, SourceResolver) + argv/stdin/stdout/stderr
```

Зависимости — только вниз по списку: `meridian-cli` зависит от `meridian-app`
и `meridian-storage-sqlite`; `meridian-app` зависит от `meridian-core`;
`meridian-core` ни от одного из трёх других крейтов не зависит.
`#![forbid(unsafe_code)]` действует на уровне всего workspace
(`meridian-rust-sqlite-architecture.md` §11).

Ровно четыре крейта. `meridian-cli` — не только точка входа: он же корень
композиции (composition root) всего workspace и единственное место, где
собираются вместе конкретные реализации портов и передаются в `meridian-app`.
Он поэтому неизбежно знает больше, чем один только argv/stdin/stdout/stderr —
он знает про файловую систему, Git и переменные окружения ровно постольку,
поскольку это единственный крейт, где локальным адаптерам этих портов вообще
разрешено жить (см. §3.1). Это не нарушает границу «один крейт — один
внешний мир»: `meridian-storage-sqlite` по-прежнему остаётся единственным
крейтом, знающим про SQLite, а `meridian-core` — по-прежнему без единого
знания о файлах, Git, БД, сети или env.

## 2. `meridian-core` — предметное ядро

Синхронный домен без побочных эффектов. Несёт:

- типы предметной области (§5);
- resolver — вычисление применимых норм, протоколов и блокеров из контекста
  задачи, репозитория, путей, профилей и объявленной применимости (тот же
  контракт, что и сегодняшний `scripts/rule-resolver.mjs`, перенесённый
  построчно, а не переосмысленный);
- обнаружение и представление конфликтов норм;
- планы миграции — структуры данных и проверки контракта
  `instance-data-migration.md` (девять свойств: нейтральность к хранилищу,
  точный источник, полное соответствие, сохранение семантики, обратимость,
  проверяемое соответствие, повторяемость, закрытая форма, интеграция
  проверки);
- доказательства (`evidence`) — структуры и правила связывания утверждения с
  проверяемым результатом;
- вердикты и диагностику — `Verdict`, `Diagnostic` и их агрегацию для вывода.

**Явные ограничения.** `meridian-core` не открывает файлы, не обращается к
Git, не обращается к базе данных, не выполняет сетевые вызовы, не читает
переменные окружения и не производит вывод (ни в stdout/stderr, ни в лог).
Всё перечисленное — на стороне `meridian-app` (порты) и адаптеров
(`meridian-storage-sqlite`, `meridian-cli`). Каждая проверка, требующая
внешних данных, принимает их как уже загруженные структуры и параметры
функции, а не читает их сама.

## 3. `meridian-app` — прикладные операции и порты

Оркестрирует `meridian-core` через порты, не зная деталей их реализации.
Операции:

- **import** — управляемый приём внешних правил и данных Экземпляра
  (перенос `controlled-rule-intake.mjs`, `existing-project-compatibility-mode.mjs`);
- **validate** — эквивалент `scripts/kernel-validate.mjs`;
- **resolve** — эквивалент `scripts/rule-resolver.mjs`, вызывающий resolver
  `meridian-core`;
- **migration plan / apply / verify / rollback** — реализация контракта
  `instance-data-migration.md` поверх `RecordRepository`;
- **export** — канонический экспорт в JSON (та же форма, что уже определяет
  `scoped-record.schema.json`).

**Порты** (traits, определяемые здесь; реализация — не в этом крейте, см.
«Адаптер» ниже):

| Порт | Ответственность | Адаптер |
|---|---|---|
| `RecordRepository` | Чтение и запись управляемых записей (`scoped-record`) в постоянное хранилище | `meridian-storage-sqlite` |
| `EvidenceRepository` | Хранение и разрешение доказательств (`evidence_ref` → проверяемая запись) | `meridian-storage-sqlite` |
| `SourceResolver` | Разрешение внешних ссылок на источники — тот же приём «закрытого ответа трансформера», что уже применяют `resolveSource`, `resolveSourceSnapshot`, `resolveEvidence` в текущей Node-реализации (`instance-data-migration.md` §2, §5, §6) | `meridian-cli` |
| `GitInspector` | Чтение состояния Git-репозитория (ревизия, дайджест, чистота рабочего дерева) без внешнего процесса `git` | `meridian-cli` |
| `WorkspaceReader` | Чтение файлов рабочего дерева, не относящихся к SQLite-хранилищу, — нормативные документы Kernel, `instance-template/`, `product.yaml`, конфигурация, схемы реестров, `PIN.yaml` скиллов; `meridian-app` не открывает файлы напрямую ни для одной операции | `meridian-cli` |
| `Clock` | Источник текущего времени — вынесен портом, чтобы `meridian-core` и `meridian-app` оставались детерминированными в тестах | `meridian-cli` |

`meridian-app` **определяет** порты и **оркеструет** вызовы к ним; он не
реализует ни один порт сам и не содержит ни одного адаптера. Любая проверка,
которая сегодня в Node-реализации обращается к файлу, Git, часам или базе
напрямую, в Rust проходит через соответствующий порт, реализованный в
`meridian-storage-sqlite` или `meridian-cli` (§3.1).

### 3.1. Владение адаптерами

Порт (trait) и его реализация (адаптер) — разные вещи и живут в разных
крейтах:

- **`meridian-storage-sqlite`** реализует ровно два порта, оба обращающиеся к
  SQLite: `RecordRepository` и `EvidenceRepository`. Он не реализует
  `SourceResolver`, `GitInspector`, `WorkspaceReader` или `Clock` — это не его
  внешний мир.
- **`meridian-cli`** реализует все остальные порты — `SourceResolver`,
  `GitInspector`, `WorkspaceReader`, `Clock` — то есть все локальные адаптеры,
  которым нужны файловая система, Git или окружение конкретной машины, но не
  SQLite. Это следствие того, что `meridian-cli` — единственный корень
  композиции workspace (§1): у порта, реализация которого не хранилище,
  просто нет другого крейта, где ему было бы уместно жить, кроме крейта,
  который и так собирает конкретный запуск.
- **`meridian-app`** не реализует ни одного порта: он принимает уже
  собранные реализации (через dependency injection на старте `meridian-cli`)
  и вызывает их через типаж, никогда не создавая конкретный тип адаптера
  сам.
- **`meridian-core`** не знает о существовании портов вообще — он принимает
  уже загруженные структуры данных как параметры функций (§2).

Если в будущем появится второй адаптер хранения (например при подключении
PostgreSQL, вне объёма текущего цикла) или второй фронтенд поверх `meridian-app`
(вне объёма текущего цикла), он получает свой собственный крейт с реализацией
нужных ему портов — расширение происходит добавлением нового крейта или новой
реализации существующего порта, а не переносом логики адаптера в
`meridian-app` или `meridian-core`.

## 4. `meridian-storage-sqlite` — хранилище

Единственный крейт, которому известно о существовании SQLite. Реализует
`RecordRepository` и `EvidenceRepository` из `meridian-app`.

### 4.1. Схема

| Таблица | Назначение |
|---|---|
| `schema_migrations` | Журнал применённых миграций схемы самой SQLite-базы (не путать с `migration_runs` — миграцией данных Экземпляра) |
| `records` | Текущее состояние управляемых записей (`scoped-record`): `id`, `record_type`, `scope`, `origin`, `authority`, `payload`, ссылка на текущую `record_revisions` |
| `record_revisions` | Неизменяемые редакции записей — каждое изменение добавляет новую строку, ни одна существующая не редактируется и не удаляется |
| `sources` | Зарегистрированные источники инструкций и данных (`instruction-source-registry.md`) — путь, редакция, дайджест, формат, канал чтения |
| `evidence` | Неизменяемые доказательства (`evidence_ref` → проверяемая запись, `instance-data-migration.md` §6) |
| `owner_decisions` | Решения владельца (`owner-decision`), на которые ссылаются `authority.decision_ref` записей |
| `execution_runs` | Состояние запусков (`execution-run`, многоосевая модель — этап, рабочее состояние, участники, блокеры, следующий шаг) |
| `migration_runs` | Факт и результат конкретного применения плана миграции данных (`instance-data-migration.md`), включая связь с `plan_fingerprint` и `idempotency_key` |

### 4.2. Инварианты

- **Транзакционная запись.** Каждая операция, которая должна быть атомарной с
  точки зрения предметной области (например: минт записи и создание её
  первой редакции), выполняется в одной SQLite-транзакции; частичная запись
  при сбое отсутствует.
- **Foreign keys включены** (`PRAGMA foreign_keys = ON`) на каждом открытии
  соединения — без этого SQLite не проверяет ссылочную целостность даже при
  наличии `REFERENCES` в схеме.
- **Неизменяемые редакции и доказательства.** `record_revisions` и `evidence`
  — только append: строки не обновляются и не удаляются операциями
  прикладного уровня; исправление означает новую строку, а не правку старой
  (тот же принцип, что уже действует для `payload.rollback.rewrites_published_history:
  false` в `instance-data-migration.md` §5).
- **Идемпотентный импорт.** Повторный `import` с тем же источником и той же
  редакцией не создаёт вторую копию — тот же принцип детерминированного
  `idempotency_key`, который уже вычисляет `computeIdempotencyKey`
  (`instance-data-migration.md` §7), переносится в схему SQLite как
  уникальное ограничение на соответствующий столбец.
- **Резервная копия.** Механизм резервного копирования базы — часть адаптера
  хранения (например `VACUUM INTO` на снимок файла); он не входит в
  предметное ядро и не влияет на структуру портов.
- **Канонический экспорт.** Экспортированный JSON не содержит артефактов
  SQLite (rowid, внутренние ключи) — только поля канонического конверта
  записи (`id`, `title`, `record_type`, `scope`, `origin`, `authority`,
  `payload`), та же форма, что уже проверяет `scoped-record.schema.json`.
- **Секреты не сохраняются.** Ни одна таблица не хранит значение секрета;
  запись содержит только допустимую ссылку на внешнее защищённое хранилище
  (тот же принцип, что уже действует для рабочих данных,
  `workspace-scope-model.md` §4).
- **Путь БД не является идентичностью области.** Расположение файла SQLite —
  свойство адаптера хранения конкретной машины; область, происхождение и
  полномочие записи не зависят от того, где лежит файл, как этот же принцип
  уже действует для физического репозитория (`workspace-scope-model.md`,
  `kernel-boundary.md`).

## 5. Типы

| Тип | Смысл |
|---|---|
| `SemanticId` | Стабильный `kebab-case` идентификатор governed entity (`operating-principles.md` §2) |
| `WorkspaceId` | Идентификатор рабочего пространства проекта |
| `RepositoryId` | Идентификатор локальной области репозитория |
| `Revision` | Точная ревизия источника (например Git-ревизия) |
| `ContentDigest` | Криптографический дайджест содержимого (алгоритм + значение, закрытая форма — как уже требует `instance-data-migration.md` §2 для `digest`) |
| `EvidenceRef` | Непрозрачная ссылка на доказательство, разрешаемая через `EvidenceRepository` |
| `Scope` | Область записи по `workspace-scope-model.md` §1 (одна из шести) |
| `Origin` | Происхождение записи (`kind`, `source_ref`) по `scoped-record.schema.json` |
| `Authority` | Полномочие записи (`kind`, `authority_ref`, `decision_ref`) |
| `Verdict` | Итоговый результат проверки (`VERIFIED`/`UNVERIFIED`/`BLOCKED` и аналогичные закрытые наборы конкретных контрактов) |
| `Diagnostic` | Одно сообщение проверки — уровень (FAIL/WARN/INFO), затронутый путь или запись, текст |

Каждый тип реализует строгое построение (валидация на границе конструктора,
не на every use site) — синтаксически допустимое, но семантически неверное
значение (пустая строка там, где нужен непустой `SemanticId`; POSIX-путь там,
где нужна непрозрачная ссылка) не должно доходить до предметного ядра
конструктором по умолчанию.

## 6. Разделение уровней проверки

Каждый входной контракт проходит четыре различимых уровня, не смешиваемых в
одной функции:

1. **Транспортные структуры данных** — то, что десериализуется из JSON/YAML
   без знания предметного смысла (serde-структуры на границе).
2. **Синтаксическая проверка** — форма без смысла: обязательные поля,
   допустимые перечисления, ограничения формата (аналог JSON Schema слоя
   сегодняшней Node-реализации).
3. **Предметная проверка** — смысл с учётом контекста: покрытие, слияние,
   полномочие цели, проверяемость, повторяемость (аналог `checkCoverage`,
   `checkTargetGroups`, `checkVerification`, `computePlanFingerprint` в
   `scripts/lib/instance-data-migration.mjs`).
4. **Валидные предметные типы** — результат, с которым дальше работает
   `meridian-core`; построение такого значения возможно только после
   прохождения уровней 2–3.

Уровень 1 и 2 могут жить в `meridian-app` (граница с внешним миром); уровень 3
и 4 — граница между `meridian-app` и `meridian-core`, где смысл уже
предметный, а не транспортный.

## 7. CLI (`meridian-cli`)

| Команда | Действие | Изменяет состояние |
|---|---|---|
| `init` | Инициализация локального рабочего пространства и файла SQLite | да |
| `doctor` | Проверка проводки (эквивалент `preflight`) и состояния хранилища | нет |
| `import` | Приём внешних правил и данных Экземпляра | да |
| `validate` | Полная проверка гейта | нет |
| `resolve` | Разрешение применимых норм для заданного контекста | нет |
| `migration plan` | Построение плана миграции | **нет** — план не изменяет состояние |
| `migration apply` | Применение плана | да; поддерживает `--dry-run` и требует явного подтверждения без него |
| `migration verify` | Проверка результата применённой миграции | нет |
| `migration rollback` | Обратимое восстановление по `payload.rollback` | да |
| `export` | Канонический экспорт в JSON | нет |

Правила, общие для всех команд:

- `--format human|json` — обе формы поддерживаются каждой командой, которая
  производит структурированный результат;
- результат команды — в stdout; диагностика, прогресс и предупреждения — в
  stderr; смешение этих двух каналов для одного и того же содержимого не
  допускается;
- коды завершения стабильны и документированы для каждой команды (0 —
  успех, отдельные ненулевые коды — для FAIL проверки, для ошибки окружения,
  для отказа предметной проверки — точный список фиксируется на этапе
  реализации, не в этом документе, но сам принцип стабильности — часть
  спецификации);
- `migration plan` **не** открывает запись на изменение и не создаёт строк в
  `migration_runs` — это чистая функция от текущего состояния и входа;
- `migration apply` без `--dry-run` требует явного подтверждения (интерактивного
  либо флагом, фиксируется при реализации) прежде чем изменить хранилище.

## 8. Что эта спецификация не делает

- не выбирает конкретные Rust-крейты (сериализация, JSON Schema, SQLite-драйвер);
- не назначает точные коды завершения и точные имена флагов CLI сверх
  перечисленных в §7 команд — это уточняется на этапе реализации в рамках
  пакетов `meridian-cli-foundation`/`meridian-cli-migration`
  (`meridian-rust-migration-program-plan.md`);
- не начинает фактическую реализацию ни одного из четырёх крейтов;
- не изменяет контракт `instance-data-migration.md` — она реализует его
  девять свойств на SQLite, не переопределяет их;
- не выбирает PostgreSQL, сеть или многопользовательский доступ
  (`meridian-rust-sqlite-architecture.md` §6, §14).
