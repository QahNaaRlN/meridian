# SKILL: Bugfix Protocol

## Назначение

Skill решает одну задачу: исправленный баг должен оставить после себя
regression assertion, который **доказанно** падал на дефектной реализации.

Skill не про coverage. Дополнительные тесты сверх минимума — нарушение, а не заслуга.

---

## Шаг 0. Проверка типа задачи

Прежде чем начинать — убедись, что это действительно BUGFIX.

```
BUGFIX          поведение существует, оно неправильно относительно
                уже действующего контракта, задача его восстанавливает

FEATURE         поведения раньше не было           → skill test-planning

BEHAVIOR_CHANGE контракт меняется намеренно,
                есть ссылка на решение             → skill test-planning
```

Выведи и включи в отчёт:

```
Change type: BUGFIX
Источник expected contract: <Confluence | AC задачи | Zod-схема |
                             существующий тест | API-контракт | отсутствует>
```

**Дефолт:** если контракт процитировать нельзя, но поведение существует и
признано неправильным — это BUGFIX.

**Неоднозначность → СТОП, спроси человека.** Не выбирай удобную ветку сам.

---

## Шаг 1. REPRODUCE

Не трогай production-код. Сначала зафиксируй:

```
Входные условия:
Ожидаемое поведение:
Фактическое поведение:
Нарушенный инвариант:
```

Инвариант — в доменных терминах, без имён функций и файлов.

```
✅ Отменённая операция не может быть сохранена.
❌ getOperationPermissions возвращает canSave: true при статусе cancelled.
```

Если инвариант не формулируется без упоминания кода — дефект ещё не понят.

---

## Шаг 2. RED

Создай новое **или аддитивно расширь** существующее behavioral assertion.

### Выбор слоя

Минимальный слой, где наблюдаем **инвариант**, а не тот, где лежит дефектный код.

```
unit → component → integration → E2E
```

Вопрос: «где дешевле всего достоверно наблюдать нарушенное поведение».
Баг физически в `getOperationPermissions`, инвариант «нельзя сохранить» →
скорее всего component-тест.

E2E — только если ниже дефект не ловится.

### Мок

```
❌ баг в расчёте прав → права замоканы → проверяем кнопку
```

Мокай окружение, не дефектную логику.

### Что значит «расширить»

```
добавить строку в it.each                        → можно
добавить новый expect в существующий блок        → можно
изменить ожидаемое значение в существующей строке → СТОП, спроси человека
изменить или удалить существующий expect          → СТОП, спроси человека
```

### Именование и провенанс

```ts
// новое утверждение
describe('regression', () => {
    // PROJ-1234
    it('не позволяет сохранить отменённую операцию', () => { … })
})

// расширение существующего
it.each([
    ['active',    true],
    ['completed', false],
    ['cancelled', false], // regression PROJ-1234
])(…)
```

Имя описывает поведение. Номер задачи в имени — нельзя.

### Получение evidence (КРИТИЧНО)

```
1. production-код БЕЗ фикса
2. запустить ровно это assertion
3. скопировать вывод: имя теста + текст assertion error
```

**Не считается RED:**

```
✗ Cannot find module './operations'
✗ Timeout - Async callback was not invoked
✗ TypeError: Cannot read properties of undefined
```

Это ошибка окружения, а не доказательство. Переписывай тест.

**Считается RED:**

```
✗ не позволяет сохранить отменённую операцию
  expected element to have attribute "disabled", received null
```

Если фикс уже внесён — откати production-код, тестовый файл оставь, получи вывод.

```
✋ СТОП

RED получен. Покажи вывод раннера и дождись подтверждения,
прежде чем переходить к исправлению.
```

---

## Шаг 3. DIAGNOSE MISS

Почему существующий suite это пропустил? Выбери из списка:

```
[ ] покрытие отсутствовало
[ ] тест был, но не содержал нужную границу / класс эквивалентности
[ ] mock или stub скрыл дефектную логику
[ ] тест был на неподходящем слое
[ ] тест проверял детали реализации вместо поведения
[ ] тест был skipped, disabled или flaky
[ ] не классифицируется — СТОП, спроси человека
```

Причин может быть несколько — пометь основную. Свободный текст вместо выбора нельзя.

Это только запись. Переделывать suite в текущей задаче не нужно.

---

## Шаг 4. FIX

Минимальное изменение, устраняющее root cause.

Нельзя в этом же MR: рефакторинг, переименования, форматирование, попутные улучшения.

Если существующий тест противоречит фиксу:

```
✋ СТОП

Существующий тест противоречит исправлению.
Тест: <файл, имя>
Что он утверждает сейчас:
Почему это утверждение неверно:
Требуется решение.
```

---

## Шаг 5. GREEN

Вывод раннера, подтверждающий:

- regression assertion проходит;
- релевантный существующий suite проходит.

---

## Шаг 6. Объём

Единица — самостоятельное поведенческое утверждение (`it`).
`it.each` на четыре границы — **одно** утверждение.

```
по умолчанию: 1
больше двух:  ✋ СТОП, ревью человека
```

Каждое утверждение сверх первого требует строки:

```
✅ Root cause затрагивает обе границы включительного диапазона.
❌ Добавлены тесты, так как покрытие модуля низкое.
```

Не делай: exhaustive-комбинации, перебор enum одного класса, snapshot вместо
behavioral assertion, копии существующих тестов, E2E при ловимости ниже,
mutation testing без просьбы.

---

## Шаг 7. Отчёт

```
Change type: BUGFIX
Источник expected contract: Confluence / Operations / Terminal states

Bug:
Отменённые операции допускали действие «Сохранить».

Инвариант:
Операция в терминальном статусе не может быть сохранена.

Root cause:
Статус cancelled отсутствовал в классификации терминальных состояний.

Почему suite пропустил:
основная: mock скрыл дефектную логику

Regression:
OperationCard.spec.ts → describe('regression') → PROJ-1234

RED (на коде с багом):
  ✗ не позволяет сохранить отменённую операцию
    expected element to have attribute "disabled", received null

GREEN (после фикса):
  ✓ не позволяет сохранить отменённую операцию

Новых утверждений: 1
Изменено существующих ассертов: нет
```

## Особый случай: баг найден внутри feature-задачи

```
не блокирует фичу  → завести задачу в трекере, НЕ чинить, продолжить фичу
блокирует фичу     → выделенный сегмент с полным циклом
```

Строка в описании MR задачей не является — нужен тикет.

**Изоляция RED.** Дефектное состояние нельзя воспроизвести в дереве с
незавершённой фичей: вывод будет получен на смеси и ничего не докажет.

```bash
git worktree add ../fix-PROJ-1234 <base-commit>
# REPRODUCE → RED → FIX → GREEN в изолированном дереве
# забрать фикс в дерево фичи, продолжить feature flow
```

---

## Пять остановок

```
1. классификация неоднозначна
2. существующий ассерт противоречит фиксу
3. regression assertion технически невозможен
4. нужно больше двух новых утверждений
5. DIAGNOSE MISS не классифицируется
```

Во всех пяти: сформулируй вопрос и остановись. Убедительное техническое
обоснование решение человека не заменяет.

---

## Выход: расхождение трёх слоёв

Если в ходе диагностики обнаружено, что требования, реализация и тесты
расходятся между собой и починка одного слоя ответом не является, протокол
**не** завершается написанием нормативного регрессионного теста.

1. Не превращай оспариваемое поведение в нормативный регрессионный тест —
   утверждающий, что оно и есть ожидаемый контракт. Characterization-тест,
   фиксирующий фактическое поведение, допустим при явной пометке и ссылке на
   запись; если тест преждевременен — `describe.todo` со ссылкой.
2. Создай Problem Record по шаблону в `<Domain> — Решения`.
3. Повесь баннеры на страницы, описывающие неверное поведение, у всех
   потребителей.
4. Прими явное решение о судьбе задачи: заблокирована до решения / чинится
   частично / закрывается как расхождение требований.

Протокол считается выполненным после публикации записи и расстановки баннеров.

## Контекст продукта

Конвенции конкретного продукта — какие библиотеки в ходу, через какой канал
идут ошибки, какие тестовые утилиты обязательны, где физически лежит
регрессионный тест — это Instance, не Kernel. Они лежат в
`$MERIDIAN_INSTANCE/skills/bugfix-protocol/context.md` и подставляются в
протокол при его применении.

Если файла нет, это блокер: реконструировать конвенции продукта по памяти
или по аналогии с другим продуктом протокол запрещает.
