# SKILL: Versioning Standard — Confluence documentation scope

## Область действия

Облегчённая версия применения Engineering Versioning Standard, **ограниченная
документами и ревью в Confluence**. Git-специфичные разделы (git tag,
submodule, CI, Docker, monorepo, agent workflow-файлы) здесь не
задействованы.

Самодостаточен — не ссылается на git-зеркало стандарта, весь нужный минимум
правил встроен ниже. Канонический полный текст (Confluence, Status:
Accepted, Version: 1.0.0) остаётся источником истины; этот skill — его
практический подмножество для одного конкретного контекста использования.

---

## Фаза 1: Нужна ли документу версия вообще

Подавляющее большинство Confluence-документов версии не имеют — только
`Status` (Фаза 2). Версия нужна, только если документ сам по себе — release
unit по смыслу стандарта:

```
1. На этот документ ССЫЛАЮТСЯ как на контракт (например: "см. Engineering
   Versioning Standard v1.0.0"), а не просто как на источник информации?
2. Существенные правки документа способны потребовать от читателей
   пересмотреть свою работу — а не просто прочитать заново?
3. У документа будет своя история версий отдельно от истории правок самой
   Confluence-страницы?
```

- Все `NO` → версия не нужна, только `Status`. Это почти все RFC, ADR,
  Problem Record, Plan, Report, обзорные/reference-документы.
- Хотя бы один `YES` → кандидат в versioned release unit. На практике это
  почти всегда — Engineering Standard; RFC/ADR получают версию только если
  сами стали устоявшимся, на который явно ссылаются, контрактом.

Если неочевидно — не решать самостоятельно, спросить автора/ревьюера.

## Фаза 2: Status (применяется всегда, версия — не всегда)

```
Draft → Proposed → Accepted → Deprecated / Superseded / Archived
```

Указывается в шапке документа явно, не выводится из содержания. Status и
версия — независимые оси: Status можно менять без версии (безверсионный
документ просто меняет Status), версия может расти внутри одного Status
(например, Draft 0.1.0 → 0.3.0).

---

## Фаза 3: Если версия нужна — SemVer и когда что бампать

```
PATCH — правки формулировок, не меняющие правило
MINOR — новое правило / новый раздел / расширение, не ломающее существующее
MAJOR — изменение или удаление уже принятого правила
```

До `Status: Accepted` — версия в диапазоне `0.x.y`. Переход в `1.0.0` —
одновременно с переходом `Status → Accepted`, не раньше.

---

## Фаза 4: Правка после Accepted (адаптация V12 под Confluence)

⚠️ **Рабочая интерпретация, не буквальный текст стандарта.** В самом
стандарте (§3.5, §31, инвариант V12) точка неизменности — git `Tag`. Для
документов, живущих только в Confluence, такого понятия нет. Пока это не
зафиксировано отдельным RFC — использовать так:

```
До Status: Accepted    — MAY редактировать в рамках итерации без bump
После Status: Accepted — любая содержательная правка MUST идти через новый
                          version bump (Фаза 3) + запись в "Историю изменений"
```

Опечатки/форматирование — не требуют bump ни до, ни после Accepted (см.
Фазу 5, порог значимости).

Если хочется другой интерпретации — это стоит закрепить отдельным RFC и
версией 1.1.0 самого стандарта, а не решать неявно на уровне skill.

---

## Фаза 5: "История изменений" (эквивалент CHANGELOG)

Обязательна для любого документа, прошедшего Фазу 1 с хотя бы одним `YES`.
Таблица прямо на странице или на дочерней:

```
| Версия | Дата       | Что изменилось                          |
|--------|------------|------------------------------------------|
| 1.0.0  | 2026-08-14 | Formal acceptance, Status → Accepted     |
```

Порог значимости — как в §29 самого стандарта: нормативные/содержательные
правки заносятся обязательно, чисто редакторские (опечатки, форматирование)
— можно не заносить.

---

## Правило остановки

Перед сохранением/публикацией правки, меняющей `Status` или версию
документа:

```
✋ СТОП

Документ: <имя>
Версионируется (Фаза 1): да / нет
Status: <было> → <стало>
Версия: <было> → <стало>, если применимо

Подтвердить перед публикацией.
```

Не пропускать эту остановку, даже если правка кажется небольшой — именно
здесь чаще всего расходятся заявленный и фактический объём изменений (см.
прецедент: CHANGELOG, утверждающий больше, чем реально сделано, — грубая
ошибка независимо от размера правки).
