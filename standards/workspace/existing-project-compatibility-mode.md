# Режим совместимости с существующим проектом

Идентификатор контракта: `existing-project-compatibility-mode`.

Контракт определяет продуктово-нейтральный режим подключения уже
существующего проекта к Meridian: обнаружение источников инструкций через
явный ограниченный план, снимок найденного через
[`instruction-source-registry.md`](instruction-source-registry.md), передачу
разобранного текста в [`controlled-rule-intake.md`](controlled-rule-intake.md)
только как кандидатов — без единой записи в файлы подключаемого проекта.
Управляемый режим (`managed`) остаётся отдельным добровольным решением
владельца и этим пакетом не реализуется.

Схема — [`existing-project-compatibility-mode.schema.json`](../../registries/operating-model/existing-project-compatibility-mode.schema.json).
Определения и нормативный смысл — здесь. Композитная проверка живёт в одной
функции
[`scripts/lib/existing-project-compatibility-mode.mjs`](../../scripts/lib/existing-project-compatibility-mode.mjs),
которую вызывают и `scripts/kernel-validate.mjs` (участок
`existing-project-compatibility-mode`), и самостоятельный набор
`test/existing-project-compatibility-mode.test.mjs`.

Контракт — **обязательная часть текущего Ядра**. Отсутствие схемы или
продуктово-нейтральных фикстур рядом с ней — ошибка проверки Ядра (`FAIL`), а
не информационный пропуск.

## 1. Режим по умолчанию — compatibility (свойство 1)

Для существующего проекта режим подключения по умолчанию —
`payload.connection_mode: compatibility`. Значение `managed` **никогда не
включается автоматически**: запись обязана нести
`payload.managed_mode_decision` — отдельное, проверяемое решение владельца с
полномочием, закреплённым за областью записи
(`project-owner` для `project-workspace`, `repository-maintainer` для
`repository-scope`). Отсутствие этого решения при заявленном `managed` —
отказ. Сама реализация управляемого режима (генерация адаптеров, передача
владения правилами) в этот контракт не входит (§9).

## 2. Нулевая запись в проект (свойство 2)

Библиотека контракта не предоставляет ни одной операции записи, изменения,
удаления или переименования файла подключаемого проекта:
`scripts/lib/existing-project-compatibility-mode.mjs` читает реальный каталог
только через `fs.lstatSync`/`fs.realpathSync`/`fs.statSync`/`fs.readFileSync`
(`scanDiscoveryPlan`) и не содержит ни одного вызова, создающего или
изменяющего файл. Схема тоже не несёт поля, которое могло бы нести операцию
записи: `payload` — замкнутый конверт (`additionalProperties: false` на
каждом уровне), и попытка добавить такое поле отклоняется как постороннее.

`scanDiscoveryPlan` закрывает файловую границу **до** любого обращения к
диску по конкретному слоту, в этом порядке: (1) слот обязан пройти
`checkPlanLocation` — некорректный слот отклоняется явно, состоянием
`invalid`, а не молча классифицируется как `missing`; (2) `containerRoot`
обязан быть непустой строкой; (3) кандидат, полученный присоединением пути
слота к **нормализованному абсолютному** корню, проверяется на строковую
принадлежность корню (`path.relative`); (4) как только по кандидату
что-то существует (`lstat`, без разыменования конечного звена), фактически
разрешённый путь (`fs.realpathSync`) кандидата и корня сравниваются —
кандидат, чья цель выходит за пределы корня через символическую ссылку в
любом месте цепочки, отклоняется тем же состоянием `invalid` и не читается.
Только после всех четырёх шагов выполняется `stat`/`read`. Носитель
`external-service` и любой необъявленный носитель к диску не обращаются
вовсе. Это — весь объём гарантии этой функции: она не защищает от подмены
корня между вызовами (TOCTOU) и не защищает от изменения файловой системы
другим процессом во время сканирования.

## 3. Ограниченное обнаружение (свойство 3)

`payload.discovery_plan` — закрытый, явный, ограниченный список кандидатов
расположения. Ядро **не обходит рекурсивно** дерево проекта: единственный
вход — этот список плюс (для отдельного адаптера) набор уже переданных
кандидатов. Каждый слот несёт устойчивый `id` — идентичность именно этого
слота плана, к которой обязаны привязываться обнаруженный источник, запись о
пропаже, запись о нечитаемости и находка, касающаяся этого расположения;
привязка по позиции в массиве не действует.

Форма слота повторяет контракт расположения
[`instruction-source-registry.md`](instruction-source-registry.md) §2.3:
`medium: file` требует `path` + `container_ref` и запрещает `service_ref` +
`resource_ref`; `medium: external-service` — наоборот. Путь нормализован и
относителен носителю: абсолютный путь, выход через `..`, обратная косая
черта как разделитель и необъявленный носитель отклоняются
(`scripts/lib/existing-project-compatibility-mode.mjs`, переиспользуя
`checkLocationPath` из `instruction-source-registry.mjs`).

Обнаруженный источник, запись о пропаже и запись о нечитаемости обязаны
называть слот плана, который они закрывают (`plan_id`/`id`), и — для
обнаруженного источника — совпадать с ним по фактическому расположению.
Расположение вне объявленного плана — отказ: обнаружение не может найти
больше, чем разрешено планом.

Исходы плана образуют **полное взаимоисключающее разбиение**: для каждого
объявленного `id` слота обязан существовать **ровно один** исход среди
`discovered_sources`/`missing_sources`/`unreadable_sources` — считая по `id`
слота, а не по позиции в массиве. Отклоняются: слот без единого исхода
(пропущенный), слот с исходом более чем в одном из трёх массивов
(пересечение) и слот с более чем одной записью внутри одного массива
(повтор) — все три формы одной и той же проверки числа исходов на слот.

## 4. Композиция с реестром источников (свойство 4)

`payload.discovered_sources` — полные записи
[`instruction-source-registry.md`](instruction-source-registry.md), а не
второй конкурирующий формат: библиотека вызывает **ту же**
`evaluateInstructionSourceRegistry` против **той же**
`instruction-source-registry.schema.json`, которую вызывающая сторона
передаёт как есть. Идентичность носителя и источника, относительный путь,
формат, редакция, SHA-256-дайджест, `recorded_state`, `divergence` и
`read_channel` — целиком предмет этого переиспользуемого контракта; здесь их
форма не копируется и не переопределяется.

Отдельно контракт требует: обнаруженный источник обязан называть слот плана,
которому он соответствует (§3), и его `divergence.status` не может быть
`source-missing`/`source-unreadable` — такой источник принадлежит
`missing_sources`/`unreadable_sources` (§7), а не `discovered_sources`.

Все четыре композиционные зависимости —
`registrySchema`, `envelopeSchema`, `sourceRegistrySchema` (реестр
источников) и `ruleIntakeSchema` (приём внешних правил) — обязательная часть
контракта **независимо от содержимого документа**: отсутствие или
неприменимость любой из них останавливает всю проверку закрыто, даже если
`discovered_sources` и `rule_candidates` пусты. Наличие данных не решает,
нужна ли схема композиции.

## 5. Композиция с приёмом внешних правил (свойство 5)

Текст обнаруженного источника достигает
[`controlled-rule-intake.md`](controlled-rule-intake.md) **только** как
запись `payload.rule_candidates[].candidate` — полная запись этого контракта,
проверяемая композицией на **той же** `evaluateControlledRuleIntake` против
**той же** `controlled-rule-intake.schema.json`. Разрешение `source_ref`
происходит через границу, которую библиотека строит из
`discovered_sources` **этого же** сканирования
(`buildSourceResolver`/`deriveSourceReference`): неизвестный `id` или
несовпадающая с текущим снимком редакция/дайджест отклоняются в точности как
того требует `controlled-rule-intake.md` §2.

Само обнаружение, снимок или повторное сканирование **не может создать**
`accepted` или `not-applicable`: запись несёт обязательное
`discovery_status` — `new` для кандидата, впервые разобранного из источника,
найденного **этим** сканированием, обязан оставаться `candidate`; только
`carried-over` (перенесённое, уже представленное ранее решение владельца)
вправе нести решённое состояние, и оно всё равно заново и полностью проверяется
композицией — совпадающего `discovery_status` недостаточно, если решение не
проходит собственные правила `controlled-rule-intake.md`.

## 6. Первоначальное сканирование (свойство 6)

Запись первоначального подключения (`scan_kind: initial`) обязана содержать:
точную область рабочего пространства и репозитория (`payload.repository`,
сверяемая с `scope` записи — §8), ограниченный план (§3), обнаруженные,
отсутствующие и нечитаемые источники (§4, §7), кандидаты правил (§5), явные
`findings` и итоговый `next_step` (§10). Отсутствующий обязательный вход не
заменяется догадкой: схема требует все перечисленные поля, пусть и пустыми
массивами там, где сканирование ничего не нашло.

На первоначальном сканировании `divergence.status` каждого обнаруженного
источника обязан быть `unknown` — сравнивать не с чем; `missing_sources`/
`unreadable_sources` не вправе заявлять `previously_known: true` — знать
заранее не о чем.

## 7. Повторное сканирование (свойство 7)

Повторное сканирование (`scan_kind: rescan`) сравнивает предыдущий и новый
снимки **средствами уже существующего контракта**: `unchanged`/`changed`
вычисляются `instruction-source-registry.mjs` из двух проверенных состояний
(§4), `unknown` при неполных данных недопустим, а `source-missing`/
`source-unreadable` переносятся в `missing_sources`/`unreadable_sources` этого
контракта.

Изменение обязано создавать **новую находку**: обнаруженный источник со
`status: changed` без записи `findings[]` вида `source-changed` для того же
слота плана — отказ; отсутствующий источник, заявленный `previously_known:
true`, без записи `source-missing` — отказ; каждая запись `unreadable_sources`
обязана нести запись `source-unreadable`. Ни снимок, ни решение, ни
нормализованная запись не переписываются молча: изменённая редакция никогда
не проходит без явного следа.

## 8. Точная область (свойство 6)

`payload.repository` называет **и** рабочее пространство, **и** репозиторий
точно, и обязано совпадать с `scope` записи: при `scope.type:
project-workspace` — `payload.repository.workspace_id` равен `scope.id`; при
`scope.type: repository-scope` — оба поля `payload.repository` равны
соответствующим полям `scope`. Область записи ограничена этими двумя из шести
логических областей ([`workspace-scope-model.md`](workspace-scope-model.md)
§1) — сканирование не описывает встроенную методологию, профиль пользователя
или организации, эпизодическое состояние запуска.

Сама запись сканирования несёт `origin.kind: declared` (явный акт
подключения проекта) и `authority.kind: delegated-run` (сканирование ведёт
запуск, а не решение владельца) — она сама никогда не является решением
владельца; отдельные решения (`managed_mode_decision`, `owner_decision`
кандидата) несут собственное, соответствующее области полномочие.

## 9. Что этот контракт не делает

- не мигрирует данные действующего Экземпляра — предмет отдельного пакета
  `instance-data-migration`;
- не генерирует `AGENTS.md`, `CLAUDE.md` или правила Cursor;
- не изменяет ни одного файла подключаемого проекта (§2);
- не реализует управляемый режим — только проверяет, что он не включается
  автоматически (§1);
- не создаёт пользовательский интерфейс;
- не встраивает продуктовые имена, URL или абсолютные машинные пути;
- не начинает `workspace-compatibility-qualification`, выпуск обновлённого
  Meridian или Concord.

## 10. Конфликты, неоднозначность и следующий шаг (свойства 8, 10)

Конфликтующие кандидаты, несовместимые области кластера дублей,
неразрешённое происхождение, неизвестный источник или неполное решение
останавливают композицию `controlled-rule-intake` целиком — порядок чтения
записей не выбирает победителя (переиспользуется симметричный граф
конфликтов и кластеризация по `semantic_key`, `controlled-rule-intake.md`
§5–§8).

`payload.next_step` — детерминированная функция набора `findings` с одним
закрытым приоритетом (`computeNextStep`), а не мягким делением на
«блокирует/не блокирует»:

1. если есть блокирующая находка `conflict` → `resolve-conflict`;
2. иначе если есть блокирующая находка `ambiguous-scope` →
   `resolve-ambiguity`;
3. иначе если есть любая другая блокирующая находка (`unresolved-decision`,
   `source-changed`, `source-missing`, `source-unreadable`, `other`) →
   `await-owner-decision`;
4. иначе → `continue-compatibility-mode`.

Один и тот же набор `findings`, в любом порядке, обязан вычислять ровно одно
значение — функция построена на `Array#some`, поэтому порядок элементов не
влияет на результат.

Автоматически читаемый агентом источник (`read_channel.kind: agent-native`)
остаётся отдельным, не полностью наблюдаемым Meridian каналом: это уже
проверяет переиспользуемый `instruction-source-registry.mjs` (§4) —
`agent_auto_read: true` обязан сопровождаться `meridian_visibility` `partial`
или `none`, никогда `full`. Ни это, ни `controlled-rule-intake` не выводят
канал из имени файла или формата.

## 11. Изменение контракта

Добавление, удаление или изменение смысла поля — изменение универсальной
нормы Ядра: оно требует записи в журнале изменений и учитывается при выборе
следующей версии.
