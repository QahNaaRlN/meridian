# Версионирование выпусков

Нейтральное ядро темы `release-versioning`. Стандарт отвечает на вопрос **как
обозначается выпуск**: правило номера, момент его повышения, состав записи об
изменении. Он не назначает **момент выпуска** — решение выпускать принимает
владелец, а не расписание и не этот файл.

Поток веток, в котором выпуск готовится, описан отдельно
(`version-control-flow.md`).

Правила номера в этом стандарте — правила **repository-level** версии
репозитория в **режиме `semver-release`** (`version-control-flow.md` §1.3).
Репозиторий в режиме `revision-promotion` — Instance, пока владелец не принял
решение распространять его как SemVer-продукт, — repository-level номера не
ведёт: его принятое верхнеуровневое состояние идентифицируется Git SHA
advancement commit (§8). Вложенные независимо версионируемые единицы такого
репозитория (`version-control-flow.md` §1.4) продолжают вести свои номера.

## 1. Kernel — самостоятельная релизная единица

Kernel версионируется по [SemVer](https://semver.org/spec/v2.0.0.html)
собственной линией, независимой от Instance и от любого продуктового
репозитория (`COMPATIBILITY.md`). Совместимость Kernel и Instance
**объявляется** в `COMPATIBILITY.md`, а не выводится из близости номеров.

Kernel как репозиторий работает в режиме `semver-release`
(`version-control-flow.md` §1.3): всё, что ниже, — правила repository-level
версии Kernel в этом режиме. Вложенная единица `stack-profiles/` ведёт свою
линию сама (§8, `version-control-flow.md` §1.4).

## 2. Источник версии — файл `VERSION`

Действующая версия Kernel хранится в одном месте — файле `VERSION` в корне
репозитория. Никакой другой файл её не дублирует. Тег, заголовок в
`CHANGELOG.md` и запись в `COMPATIBILITY.md` — производные от `VERSION` на
момент выпуска, а не независимые объявления того же числа.

## 3. Changelog по Keep a Changelog

История изменений ведётся в `CHANGELOG.md` в формате
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/): секции по версиям в
обратном хронологическом порядке, изменения сгруппированы по типу (`Added`,
`Changed`, `Fixed`, `Removed` и т. д.), прошлые записи не переписываются.

## 4. Незавершённая работа сначала попадает в `Unreleased`

Каждый принятый пакет добавляет свои записи в секцию `## [Unreleased]`
`CHANGELOG.md` — и только туда. Пока пакет не выпущен, он не получает номера
версии и не создаёт заголовок версии.

Обычная `feature/<slug>`-ветка **не изменяет `VERSION`**. Ветка, которая
одновременно правит `VERSION` и несёт обычный пакет, смешивает подготовку
выпуска с работой над содержанием — два разных предмета в одной ветке.

## 5. Что делает `release/<semver>`-ветка

Повышение версии происходит в `release/<semver>`-ветке (`version-control-flow.md`
§2.2) и больше нигде. В этой ветке приводятся в согласованное состояние три
артефакта, и релиз не считается подготовленным, пока согласованы не все три:

1. **`VERSION`** — записан новый номер по §7;
2. **`CHANGELOG.md`** — секция `## [Unreleased]` превращается в
   `## [X.Y.Z] — YYYY-MM-DD`, над ней заводится новая пустая `## [Unreleased]`;
3. **`COMPATIBILITY.md`** — если выпуск меняет то, на что вправе рассчитывать
   Instance, добавляется строка совместимости для новой версии; если не меняет,
   это фиксируется явно в записи об изменении, а не подразумевается.

## 6. Release advancement commit и тег

После приёмки `release/<semver>`-ветки:

- **стабильная линия** (для Kernel — `master`; роль и имя — `version-control-flow.md`
  §1) продвигается по first-parent **отдельным merge-коммитом** — release
  advancement commit (`version-control-flow.md` §1.1, §2.2), без fast-forward;
- **аннотированный тег** `vX.Y.Z` (с префиксом `v`) ставится на этот
  merge-коммит и обозначает целостный snapshot итогового состояния;
- то же состояние возвращается в интеграционную линию (`develop`)
  (`version-control-flow.md` §2.2).

Отдельный package-коммит, вошедший в выпуск через merge ancestry, собственного
номера версии и собственного тега не получает: на выпуск приходится один
аннотированный тег — на его release advancement commit.

Тег аннотированный, а не легковесный: он несёт автора, дату и сообщение и сам
является объектом истории. Кто выполняет команду тега — вопрос потока
(`version-control-flow.md` §5), а не этого стандарта.

## 7. Правило выбора MAJOR / MINOR / PATCH

Номер — `MAJOR.MINOR.PATCH`. Правило однозначное и не оставляет выбор на
интуицию.

### 7.1. Пока Kernel в `0.x`

- **MAJOR остаётся `0`.** Переход `0.x → 1.0.0` — отдельное явное решение
  владельца о приёмке (`README.md` §6, открытое решение D-5), а не следствие
  накопленного объёма или истечения времени.
- **MINOR** (второе число) повышается на любой выпуск, который добавляет норму,
  схему, проверку гейта или **меняет смысл** уже действующего правила, а равно
  на любой выпуск, относительно которого `COMPATIBILITY.md` объявляет ломающее
  изменение для Instance. Пока Kernel в `0.x`, любой MINOR вправе сломать
  Instance, и Instance пиннит точную версию Kernel (`COMPATIBILITY.md`).
- **PATCH** (третье число) повышается только на выпуск, который **не меняет
  смысла ни одного правила и не трогает совместимость**: исправление опечаток и
  ссылок, уточнение формулировки без изменения нормы, приведение поведения
  валидатора в соответствие уже описанному правилу.

### 7.2. После `1.0.0`

Действует полный SemVer относительно контракта совместимости:

- **MAJOR** — ломающее изменение в терминах `COMPATIBILITY.md`; «ломающее»
  берётся из этого контракта, а не выводится по ощущению;
- **MINOR** — обратно совместимое добавление;
- **PATCH** — обратно совместимое исправление.

### 7.3. Hotfix и номер

`hotfix/<slug>` (`version-control-flow.md` §2.4) допустим **только** для
изменения, которое по правилам этой релизной единицы (§7.1–§7.2) соответствует
**PATCH**: не меняет смысла ни одной нормы, ни одной схемы, контракта гейта и
совместимости.

- hotfix повышает **PATCH** и проходит полный выпуск §5–6: согласованные
  `VERSION`, `CHANGELOG.md`, `COMPATIBILITY.md`, release advancement commit в
  стабильную линию (§6), аннотированный тег `vX.Y.Z`, возврат в интеграционную
  линию.
- Срочность сама по себе не разрешает занизить номер.
- Если исправление меняет смысл нормы, схемы, контракта гейта или совместимости
  и потому требует **MINOR** или **MAJOR**, оно **не выпускается как hotfix**:
  готовится `release/<semver>` соответствующего номера обычным порядком
  (`version-control-flow.md` §2.2).

## 8. Другие релизные единицы

Meridian состоит из независимо версионируемых единиц; общей линии версий у них
нет (`COMPATIBILITY.md`).

- **`stack-profiles/`** — вложенная независимо версионируемая единица
  (`version-control-flow.md` §1.4) с собственными `VERSION` и `CHANGELOG.md`,
  версионируется независимо от repository-level `VERSION` Kernel
  (`stack-profiles/README.md`). Этот стандарт на её номер не влияет; правила §3,
  §4 и §7 она применяет к своей линии сама. `semver-release` репозитория Kernel
  её линию не поглощает.
- **Instance** — использует **Git revision**, а не repository-level SemVer.
  Repository-level номер Instance получает только если и когда владелец примет
  отдельное решение распространять его как SemVer-продукт (`COMPATIBILITY.md`).
  До такого решения ссылка на верхнеуровневое состояние Instance — это ревизия,
  а не версия. Продвижение выполняется в режиме `revision-promotion`
  (`version-control-flow.md` §1.3, §2.3): ветка `promotion/<slug>`, отдельный
  non-fast-forward promotion advancement commit, идентификатор — его Git SHA,
  без repository-level `VERSION` и без repository-level тега `vX.Y.Z`. Общее
  правило типа не заменяет локальное объявление: каждый конкретный Instance
  обязан объявить режим и имена своих линий в собственном tracked-источнике, и
  до этого Git-интегратор fail-closed (`version-control-flow.md` §5.2).
  Собственный SemVer вложенных единиц Instance режим репозитория не отменяет.
- **Завендоренные зависимости** (`skills/<name>/`) привязаны к неизменяемому
  SHA-256 в `PIN.yaml`. Это пин, а не номер версии: смена пина — изменение
  Kernel и требует записи в `CHANGELOG.md` (`COMPATIBILITY.md`).
- **Smoke-пакет** Instance — вложенная независимо версионируемая единица
  (`version-control-flow.md` §1.4): несёт собственный SemVer по своей природе
  (`COMPATIBILITY.md`), и `revision-promotion` репозитория Instance его не
  отменяет и не переопределяет.

## 9. Что этот стандарт не описывает

- **Момент выпуска.** Когда готовить `release/<semver>` — решение владельца.
- **Поток веток и запреты прямой записи** — `version-control-flow.md`.
- **Переход `0.x → 1.0.0`** по существу — открытое решение D-5 (`README.md` §7);
  здесь зафиксировано только то, что он требует явного решения.
- **Версионирование опубликованных страниц канонического wiki** — принятый
  skill `skills/versioning-standard-docs/SKILL.md`; это другой предмет с другой
  цепочкой статусов.
- **Продуктовые релизы и их CI** — вне области Kernel (`COMPATIBILITY.md`).
