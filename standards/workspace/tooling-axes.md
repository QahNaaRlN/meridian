# Tooling axes: documentation, task tracker, repository hosting

Kernel определяет три оси интеграции, для которых у продукта всегда есть конкретный инструмент, способ доступа и ограничения — но какие именно, Kernel не знает и не должен предполагать по умолчанию:

1. **Документация (documentation tooling)** — где ведётся каноническая документация и как агент с ней взаимодействует (MCP, прямой API, браузер, ручной экспорт).
2. **Таск-трекер (task tracker)** — где ведутся задачи/тикеты, cloud или self-hosted, точный базовый URL.
3. **Репозиторий (repository hosting)** — где хостятся репозитории, self-hosted или cloud, и — раздельно — какой транспорт разрешён для Git-операций (`git_transport`) и какова политика доступа к API хостинга (`api_access`).

Конфигурация всех трёх осей — Instance, не Kernel: `$MERIDIAN_INSTANCE/product.yaml`, блок `tooling`. Kernel-документы не хардкодят вендора, URL или протокол ни для одной оси.

## Правило

Прежде чем агент обращается к инструменту любой из трёх осей, он читает соответствующую запись `tooling.<axis>` в `product.yaml` и следует ей буквально, включая явные ограничения (`constraint`). В частности:

- **Self-hosted vs cloud не предполагается.** Если `hosting: self-hosted` и указан `base_url`, использовать только этот URL. Дефолтный cloud-адрес вендора (например `*.atlassian.net` для Jira) не пробуется ни как fallback, ни как эвристика.
- **Протокол доступа не предполагается.** Если поле ограничивает соединение (например `git_transport: ssh`), альтернативный транспорт не используется — ни для клонирования, ни как временная мера.
- **Транспорт Git и доступ к API — разные оси, и одна не выводится из другой.** `git_transport: ssh` не запрещает и не разрешает REST API сам по себе; политика API фиксируется отдельно в `api_access` (`https` | `prohibited` | `unresolved`). При `api_access: unresolved` обращаться к API нельзя до явного решения владельца — но и утверждать, что он запрещён, тоже нельзя.
- **Способ интеграции не предполагается.** Если ось декларирует конкретный канал (например MCP-сервер), прямые HTTP-запросы или ручной браузерный доступ в обход этого канала не подставляются молча.
- Если `tooling.<axis>` для текущего продукта не заполнена — это `unresolved`, не повод угадать вендора или URL по аналогии с другим продуктом. Остановиться и запросить факт у пользователя, как и для любого другого `REPLACE_ME`/unresolved значения в этой системе.

## Зачем отдельная ось, а не часть `canonical_wiki`

`product.yaml.canonical_wiki` фиксирует, *где* канонический Documentation Standard (конкретная страница/пространство). `tooling.documentation` — про *как* агент туда попадает (канал доступа). Это разные факты: первый может не измениться, когда меняется MCP-коннектор, и наоборот.
