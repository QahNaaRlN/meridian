# Руководство оператора по объединённой квалификации обновления

Это переносимое, продуктово-нейтральное руководство для человека-оператора,
доводящего один задачный путь (постановку → запуск → доказательство и
передачу → полевую оценку) до итоговой квалификации интеграции пакетов 1–8
программы `meridian-operating-upgrade`
([`upgrade-integration-qualification.md`](upgrade-integration-qualification.md)).
Оно не заменяет ни один из восьми составляемых нормативных контрактов —
только объясняет порядок шагов и то, какой пакет отвечает за каждый шаг.

Руководство ничего не говорит о конкретном продукте: оно применимо к любому
рабочему пространству любого Экземпляра Meridian.

## Четыре шага

```text
TASK JOURNEY (задачный путь: постановка → запуск → передача)
  → FIELD EVALUATION (полевая оценка, опционально на момент квалификации)
  → NEUTRAL SCENARIOS (три обязательных нейтральных сценария)
  → QUALIFICATION (объединённая квалификация)
```

### 1. Task journey — задачный путь

Оператор доводит одну постановку задачи
([`task-specification.md`](task-specification.md)) через один запуск
([`execution-state-model.md`](execution-state-model.md)) до одной записи
передачи результата
([`evidence-and-handoff-contract.md`](evidence-and-handoff-contract.md)).
Этот пакет **не вводит** ни одного собственного шага для постановки,
запуска, назначения роли ([`role-and-human-control.md`](role-and-human-control.md))
или сбора контекста ([`bounded-context-manifest.md`](bounded-context-manifest.md))
— все четыре уже полностью описаны своими контрактами, и составленная
запись `evidence-and-handoff` уже композирует их (`upgrade-integration-qualification.md`
§1).

**Результат шага:** одна разрешимая запись `evidence-and-handoff` с
`outcome.status` — `complete`, `blocked` или `handed_off_incomplete`.

### 2. Field evaluation — полевая оценка

Когда для этого задачного пути уже составлен отчёт полевой оценки
([`meridian-field-evaluation.md`](meridian-field-evaluation.md)), оператор
называет его закреплённой ссылкой. Отчёт не обязателен на момент
квалификации — рабочее пространство вправе дойти до квалификации без него,
и это легальный, но не финальный исход (`upgrade-integration-qualification.md`
§2, §5 ветвь 7): владелец в этом случае ещё не получает понятного отчёта о
возможностях и известных пределах, и квалификация останавливается на
`UNVERIFIED`, ожидая составленный отчёт, а не блокируется.

**Результат шага:** закреплённая ссылка на составленный
`field-evaluation-report`, либо явный `null`.

### 3. Neutral scenarios — три обязательных нейтральных сценария

Независимо от предметной задачи шага 1, объединённая квалификация обязана
называть по одному разрешимому примеру на каждый из трёх закрытых сценариев
(`upgrade-integration-qualification.md` §3):

- **`single-module-refactor`** — постановка, классифицированная шаблоном
  `refactor-preserving-behavior`, доведённая через модель без декомпозиции.
- **`multi-repository-decomposition`** — постановка, классифицированная
  шаблоном `decompose-initiative`, чей запуск **фактически продвинулся**
  дальше этапа `classification` (декомпозиция не только названа, но
  происходит).
- **`language-change-limit-case`** — постановка о смене языка реализации,
  тоже классифицированная шаблоном `decompose-initiative`, чей запуск
  **остаётся** на этапе `intake` или `classification` — доказательство того,
  что классификация происходит, а исполнение продуктового переписывания
  — нет.

Эти три примера **не обязаны** относиться к тому же задачному пути, что шаг
1 — обычно это отдельные, специально подготовленные постановки и запуски,
демонстрирующие переносимость модели, а не предметный результат конкретной
задачи оператора.

**Результат шага:** три закреплённые пары `task_specification_ref` +
`execution_state_ref`, по одной на каждый `scenario_id`, без пропуска и без
дубля.

### 4. Qualification — объединённая квалификация

Оператор составляет **одну** запись
[`upgrade-integration-qualification.md`](upgrade-integration-qualification.md),
несущую закреплённую ссылку на составленный задачный путь (шаг 1),
закреплённую ссылку на отчёт полевой оценки либо явный `null` (шаг 2), три
закреплённые пары нейтральных сценариев (шаг 3) и закрытый
продуктово-нейтральный шаблон переходной совместимости
`workspace_transition_compatibility` (`status: kernel-template-only` в этом
Kernel-срезе — заполненное доказательство перехода конкретного продукта
пишется отдельным, более поздним пакетом Экземпляра, не здесь). Квалификация
**не принимает решений заново** — она вычисляет один закрытый вердикт
(`QUALIFIED`/`BLOCKED`/`UNVERIFIED`) из того, что уже составлено на
предыдущих трёх шагах, по закрытой матрице решений
(`upgrade-integration-qualification.md` §5).

Три возможных исхода для оператора:

- **`QUALIFIED`** — задачный путь завершён, все три нейтральных сценария
  классифицированы корректно, отчёт полевой оценки составлен. Пакеты 1–8
  демонстрируют совместную работу на этом рабочем пространстве.
- **`UNVERIFIED`** — задачный путь передан намеренно до завершения
  (`handed_off_incomplete`), либо отчёт полевой оценки ещё не составлен.
  Оператор возвращается к шагу 1 или 2.
- **`BLOCKED`** — задачный путь заблокирован, покрытие трёх сценариев не
  полно, либо хотя бы один сценарий не соответствует собственному ожиданию
  (неверный шаблон типа задачи или неверный этап жизненного цикла
  разрешённого запуска). Оператор разрешает блокирующую причину (обычно
  возвращаясь к шагу 1 или 3) прежде, чем повторить попытку.

## Что оператор никогда не делает вручную

- не заявляет `qualification_state` вручную в обход пересчитываемой матрицы
  решений §5 нормативного контракта — заявленное значение, расходящееся с
  вычисленным, отклоняется проверкой Ядра;
- не встраивает составленные записи (задачный путь, отчёт полевой оценки,
  постановку или запуск любого сценария) в саму запись квалификации —
  только закреплённые ссылки, сверяемые внешним резолвером
  (`upgrade-integration-qualification.md` §1, §6);
- не исполняет ни одной единицы продуктового переписывания ради сценария
  `language-change-limit-case` — только классификация (§3 нормативного
  контракта);
- не пишет заполненное доказательство перехода конкретного продукта на
  новую модель рабочих пространств в это поле — `workspace_transition_compatibility`
  остаётся Kernel-шаблоном до отдельного, более позднего пакета Экземпляра
  (§4 нормативного контракта).
